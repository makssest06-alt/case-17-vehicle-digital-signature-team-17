# Структура презентации

> **Историческая заметка.** Это рабочие материалы этапа **до дистилляции**.
> Числа на слайдах ниже (mAP 64.54, пороги 0.5114 / 0.6354, веса 359 МБ,
> «бэкбон заморожен») относятся к промежуточной head-only конфигурации.
> Финальная модель — **soup150s2 (model soup студентов ViT-L/16@256 l150 + s2)**: mAP@10 **0.9133** (сырой
> косинус, 357 gallery / 550 query), с DBA k=1 — **0.9211 / 0.8118** на галереях 361 / 1111 (Q17); порог
> отказа **0.8881** (строгий **0.9445**; без исключения почти-дублей), веса **1.19 ГБ**; на A5000 (draft=2, 32 потока — умолчание кода) — 19.1 мс/кадр, 157.6 FPS (README, раздел 6).
> Запасная — a10 (SigLIP 2 ViT-B/16): 0.8661, порог 0.8562 / 0.9294, 362 МБ.
> Числа 0.8961, 0.8025 / 0.8465 и 170 мс — прежнего студента (0.8961 — с постобработкой, которую запрещает
> Q38). Канонические цифры — в корневом
> [`README.md`](../README.md). Колоду нужно пересобрать
> `research/make_pitch_deck.py` на финальных результатах.

Слайд за слайдом: что на нём, какая картинка, какая цифра, что сказать вслух.
Картинки — в `research/pitch_assets/`, имена файлов указаны. Собранный файл
презентации: `research/pitch_assets/ЛЦТ2026_кейс17_команда17.pptx`
(`python research/make_pitch_deck.py`), текст доклада лежит в заметках к слайдам.

**Про слайды 7–11.** Организаторы требуют их по своему шаблону. Шаблон получен
(«ЛЦТ2026 шаблон презентации.pptx»): обязательный блок — слайды 7–11, структура
разобрана в `docs/TZ_CHECKLIST.md`, раздел 11. Содержание ниже переносится в
эту разметку как есть — текст и картинки от неё не зависят.

**Тайминг.** Рассчитано на 7 минут доклада плюс вопросы: примерно 25 секунд на
слайд, на слайдах 4, 5 и 9 — по минуте.

**Откуда цифры.** Все числа на слайдах читаются скриптами из
`research/results/*.json`. Пересчитал метрики — перезапусти
`make_pitch_assets.py` и `make_pitch_deck.py`, и слайды обновятся сами.
Руками в презентацию числа не вписываются: именно так они и расходятся.

| | |
|---|---|
| Что | Номер нечитаем: далеко, ночь, блик, ракурс. Нужен признак, который работает, когда номера нет |
| Картинка | **`10_plate_unreadable.jpg`** — четыре кадра выборки, под каждым измеренная причина |

| Сказать | Мы решаем не «распознать номер получше», а «обойтись без номера». Причина под каждым кадром — измеренная характеристика: размер рамки, яркость, доля пересвета, соотношение сторон. |

### 7. Архитектура решения

| | |
|---|---|
| Что | Кадр → рамка → кроп с запасом 10% → SigLIP base → голова с BNNeck → вектор 512D → поиск → отказ или кандидаты |
| Картинка | `11_architecture.png` |
| Цифра | вектор **512 чисел**, веса **359 МБ** при лимите 2048 |
| Сказать | Ничего экзотического: одна модель, одна голова, один индекс. Сложность спрятана в протоколе оценки и в калибровке отказа, а не в количестве блоков. |

### 9. Метрики и режим отказа

| | |
|---|---|
| Что | Качество ранжирования и отдельно качество отказа, с объяснением, почему протоколов два |

| | |
|---|---|
| Что | Три вещи, которые редко делают: лицензионная чистота, пойманные собственные ошибки, проверяемость |
| Картинка | без картинки, три крупных тезиса |

| Сказать | Все открытые ReID-датасеты для автомобилей — non-commercial. Мы это проверили по первоисточникам и обучались только на данных заказчика. И трижды поймали себя: на ускорении, на re-ranking и на том, что сервис подавал в голову ненормированный вектор — это стоило трёх пунктов mAP и нашлось за четыре дня до сдачи. У каждой цифры написано, каким скриптом она получена. |
