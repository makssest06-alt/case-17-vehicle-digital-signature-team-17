# Честная валидация (honest-eval)

> Журнал исследования 17–18.10: рабочие точки и «итоги» по ходу текста — на свою дату. Действующий профиль
> (DBA k=1, отказ raw 0.7586 / 0.9302 на протоколе Q17) — `docs/refusal.md` и корневой `README.md`, раздел 4.

Что на самом деле умеет модель из `main` на выборке, устроенной как проверка
экспертов, и откуда разрыв между нашими 0.8961 и их 0.81 / ≈ 0.32. Модели не
обучались; номер и тест ни для какого подбора не использовались.

## Что меряем

- **Протокол.** 150 машин holdout (`research/val_ids.txt`), 5 фолдов по машинам,
  в каждом фолде у 25 % машин пары в галерее нет (по ним считается TNR).
  Метрики считает эталон организаторов `research/official_evaluate.py`
  (байт в байт, junk = та же машина и та же камера, AP@10 нормирован на
  min(позитивов, 10)). Среднее ± выборочный разброс по фолдам.
- **Модель — кодом сервиса.** Векторы строит `api/app/models/registry.build_model`
  с окружением `.env.example` (или любым через `--env`), скор — сырой косинус,
  как отвечает `/v1/search`. Постобработка (`rerank` = расширение запроса +
  k-reciprocal, как в таблицах команды) считается отдельно и помечена: она
  использует другие запросы и сервису недоступна.
- **Галереи.** small (машины фолда, ~54 кадра) · 2.2k (+ весь тест чужими
  машинами) · 8996 (состав `research/GENERALIZATION_RESULTS.md`) · 10.8k (+ тест
  и кадры обучающих машин).
- **Режимы.** `official` — как эталон; «без почти-дублей» — из галереи убраны
  кадры той же машины с той же камеры (соседние кадры одного проезда), верный
  кандидат только с другой камеры. Это ближе всего к «чистой» выборке экспертов.
- **Отказ.** Порог выбирается на одном фолде и проверяется на остальных
  четырёх (`calibrate_refusal_folds.py`), recall и TNR — в семантике эталона:
  TP = принят и первый кандидат верный.

## Как запустить

Одна команда — все галереи, все режимы, таблица в markdown:

```bash
python research/honest_eval.py --data-dir <данные> --suite --tag <имя> \
  [--env REID_WEIGHTS=<веса>] [--env REID_TF_MODE=squash] [--postprocess raw,rerank,kr]
# -> research/honest_eval_results/honest_eval_<имя>_suite.md (+ .json, _folds.csv)
```

### Как Андрею сравнить raw и KNN одной командой

```bash
python research/honest_eval.py --data-dir <данные> --suite --post raw,knn --k 3 --alpha 3 --thr 0.73 \
  --tag knn_k3 [--env REID_WEIGHTS=<веса>]
# -> research/honest_eval_results/honest_eval_knn_k3_suite.md: raw и knn строками рядом на всех галереях
```

- `knn` — расширение запроса по его k ближайшим кадрам галереи (α-QE):
  `q' = L2(q + Σ max(cos(q, g_i), 0)^α · g_i)` по top-k, скор `q' · g`
  (`honest_eval.knn_expand`). Нужны только запрос и галерея, другие запросы не
  участвуют, поэтому сервис может так ответить, и отказ для `knn` считается:
  кандидат — top-1 по `knn`, решение — по сырому косинусу этого кадра против
  `--thr`. В режиме «без почти-дублей» соседи берутся без скрытых кадров той же
  машины с той же камеры.
- Параметры из командной строки: `--k`, `--alpha`, `--thr` (= `--threshold`),
  `--post` (= `--postprocess`), любой параметр постобработки — `--pp KEY=VAL`
  (`knn_k`, `knn_alpha`, `qq_k`, `csls_k`, `rerank_k1`, `rerank_k2`, `rerank_lambda`).
  С постобработкой `--tag` обязателен, иначе скрипт откажется: так не
  перезаписываются результаты `honest_eval_student*`.
- Свой вариант KNN — одна ветка `if variant == ...` в `honest_eval.scores`
  (функция от векторов запроса и галереи, параметров и маски режима) и имя в
  `ONLINE_VARIANTS`, если он считается по одному запросу.
- Пример на студенте из `main` (`honest_eval_student_knn_k3_suite.md`, k = 3,
  α = 3): mAP@10 raw → knn: 2.2k 0.704 → 0.697, 8996 0.5527 → 0.5416, 10.8k
  0.559 → 0.545; без почти-дублей при пороге 0.73 recall 0.581 → 0.554 и TNR
  0.749 → 0.771 на 2.2k. В таком виде knn на больших галереях не помогает.
  Перебирать k и α на этих же 150 машинах — подбор в выборке; выбранную точку
  проверять отдельно (другой seed фолдов, `--seed`).

### Как Андрею встроить DBA в сервис (`research/dba.py`)

```python
from dba import dba, DBAGallery            # только numpy
g2 = dba(gallery_vecs, k=1, weights="cos")  # (N, D) -> новые (N, D), L2; вход не меняется
```

`g'_i = L2(g_i + Σ max(cos, 0)·g_j)` по k ближайшим другим кадрам галереи,
запрос не меняется, скор — `q · g'`. Мерилось с k=1, weights="cos": +0.05–0.06
mAP@10 на 9.0k / 10.8k / 8996 (`bigallery_pp_a10.md`); k ≥ 4 прироста не даёт,
"uniform" на больших галереях не мерили. `research/` в образ не попадает
(`api/Dockerfile` копирует `app` и `scripts`), поэтому файл переносится в
`api/app/` целиком. Код сервиса я не трогал. Ниже — что в нём поменять.

- **Где искать.** Сейчас `/v1/search` ищет в pgvector (`db.search`, `ORDER BY
  embedding <=> q`). Индекс в памяти `api/app/gallery_index.GalleryIndex` был
  написан, ни в одной ветке не подключён и удалён 18.10 (`c16d71d`). Проще всего подключить его и
  считать DBA там: в базе остаются исходные векторы. Если хранить g' в базе
  вместо них, следующая пересборка усреднит уже усреднённое.
- **При старте:** `index.rebuild(db.fetch_all())`, внутри `rebuild` после
  нормировки — `self._vecs = dba(vecs / norms, k=1)`. Поиск — `index.search(q,
  n)` вместо `db.search`. Стоимость — kNN всей галереи на CPU Мака: `dba()` на
  10.8k кадрах — 0.3 с, на 2.2k — 29 мс, на 750 — 3.5 мс.
- **При добавлении кадра через `POST /v1/gallery`** (и `bulk-import`, `DELETE
  /v1/gallery/{id}`) — простой путь: `index.mark_dirty()` после записи в базу и
  `rebuild` перед следующим поиском. Если пересборка на каждую запись станет
  дорогой, есть `DBAGallery(vecs, k=1)`. Его `add(new)` — соседи нового кадра
  одним умножением N×D, 9 мс на кадр при 10.8k (вместе с пересчётом g' всех
  строк). Он возвращает строки, у которых поменялся g', — обновить их в
  `_vecs`. После `DELETE` — `remove(rows)`, 11 мс. Итог совпадает с `dba()` на
  той же галерее (`research/tests/test_dba.py`).
- **Порог.** `confidence` становится `q · g'`, шкала скора сдвигается.
  Порог отказа пересчитать на DBA-скорах: `python
  research/threshold_vs_gallery.py ... --score dba1`. Со штрафом за ту же камеру
  — по `cheap_bg_a10.md`.

Окружение — `api/requirements.txt` + `pandas matplotlib scikit-learn`; первый
прогон на CPU считает ~11.4 тыс. кропов (~12 мин на 8 ядрах), дальше векторы
из кэша. Тесты протокола: `python -m unittest discover -s research/tests`
(43 теста). Подробности флагов — `research/README.md`, раздел «Честная валидация».

  Предварительный итог — DBA k=1 + штраф + z100, порог 4.35: TNR 0.63–0.86 и F1 0.55–0.84 на галереях 361–10 847 кадров (порог выбран вне фолда по всем размерам сразу).
- **Дешёвый фон для штрафа** (`cheap_bg_a10.md`): вместо resnet18 (18+ мс CPU) — пиксели
  уже декодированного кадра 128×72 без машины, градиенты 64×36 + гистограммы цвета по зонам,
  1.1 мс CPU на запрос. «Та же камера» не хуже resnet18 (точность / полнота 0.92 / 0.30 против
  0.93 / 0.29), поверх DBA k=1 F1 +0.129 / +0.118 и TNR +0.080 / +0.091 на 9.0k / 10.8k
  (resnet18: +0.108 / +0.095 и +0.064 / +0.075), ≈ 106 FPS при b1 по оценке для 4060. Порог
  отказа для 8996 теперь берётся с того же фолда 9.0k: в 8996 без пары 7 запросов, у
  большинства фолдов TNR не определён, и прежний выбор давал порог ∞ (F1 0.23 вместо 0.44 у raw).

Расхождения, честно:

- **Кропы.** Эмбеддинги исследования посчитаны по готовым файлам `crops/` (тот же `crop_with_pad`, отступ 10 %, но кроп ещё раз сохранён в JPEG), сервис режет кроп из декодированного кадра в памяти. Режим `--source frames` (путь сервиса) в этих замерах не использовался, разница не мерилась.
- **Протокол «как сервис» — наше допущение:** у запроса без пары в галерее остаётся кадр его машины с той же камеры. Если в закрытой галерее таких кадров нет, вклад штрафа меньше, а порог надо брать из режима без почти-дублей.
- **Выбор по галереям с тестовыми кадрами.** k = 1 у DBA, признак фона и правило τ выбирались по результатам на галереях 9.0k / 10.8k, где тест — чужие кадры. Меток теста там нет, но тестовые картинки в выборе участвуют. Условие выбора признака («точность на отложенных камерах ≥ 0.90») добавлено после первого прогона (`cheap_bg_a10.md`).
- **8996:** без пары 7 запросов — TNR там не показатель; порог отказа для 8996 берётся с того же фолда 9.0k.
- **FPS** на 4060 не мерили (`scripts/bench_fps.sh` — для Максима); время на CPU — Мак и linux-контейнер на нём.

## Воспроизводимость (`scripts/check_reproducibility.sh`)

Прогон на ветке `ilya/honest-eval` (17.10, Mac arm64, Docker 29.4). Служебная
часть ветки (`api/`, `docker-compose.yml`, `.env.example`, `web/`, `db/`,
`scripts/`) совпадает с `glebmain` побайтно, ветка добавляет только `research/`.

| Шаг | Итог |
|---|---|
| 0–1. путь свободен, клон ветки | OK (`bf5c972`) |
| 2. состав клона, синтаксис Python | OK |
| 3. `.env`, веса в клоне (LFS, 362 МБ), `docker-compose.yml` | OK |
| 4. сборка образов | **FAIL**: pip в сборке не достучался до индекса PyTorch |
| 5–7. без сети, healthy, endpoints | не дошли |

Шаги 4–7 на этом Mac невозможны в принципе, не из-за ветки: после `glebmain`
`api/Dockerfile` требует `torch==2.5.1+cu124` (а колёс для linux aarch64 нет,
есть только x86_64), compose резервирует NVIDIA GPU. Кроме того, скрипт
использует GNU `sed -i` — на macOS прогон шёл с обёрткой `sed` в `PATH`.
Полную проверку нужно запускать на Linux x86_64 с NVIDIA Container Toolkit.
Это стоит помнить и для стенда экспертов: CPU-машина или Mac этот `glebmain`
не соберёт (вопрос из PR #6 «CPU или GPU для финала» остаётся открытым).
