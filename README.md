# Цифровой признак транспортного средства — решение команды 17

Кейс 17 · ЛЦТ 2026 · заказчик «Фалькон Тех»

Сервис сопоставляет снимки одного автомобиля с разных камер **без использования
государственного номера**, опираясь только на визуальные признаки: тип кузова,
марку и модель, цвет, геометрию, повреждения, наклейки, диски, тонировку.

Этот README соответствует пункту 12 ТЗ (требования к сопроводительной
документации) и пункту 8 (формат сдачи). Все цифры воспроизводимы одной командой.

## 1. Функциональная и компонентная архитектура

### 1.1 Функциональный путь запроса (по п.4 ТЗ)

```
[ Этап получения ]   кадр + BBox через REST API или веб-интерфейс,
                     валидация формата, размера и границ рамки
        │
        ▼
[ Этап обработки ]   кроп по BBox с запасом 10% -> squash -> бэкбон -> голова
                     -> эмбеддинг float32, L2-нормированный, 512D
        │
        ▼
[ Этап анализа ]     косинусная близость к галерее после DBA k=1 (pgvector + HNSW)
        │
        ▼
[ Этап результата ]  топ-N кандидатов с оценкой уверенности
                     ЛИБО пустой ответ (отказ), если косинус лучшего
                     кандидата без почти-дублей ниже порога (раздел 2.6)
```

### 1.2 Компонентная архитектура (по п.6 ТЗ)

Микросервисная: три независимых контейнера, связь только по сети.

```
браузер (тонкий клиент)
      │ :8080
      ▼
┌───────────────────────────────┐
│ web — nginx + одностраничный  │  выделение BBox мышью, карточки
│ интерфейс, /api/* → api       │  кандидатов, экспорт CSV/JSON
└───────────────┬───────────────┘
                │ внутренняя сеть case17net
                ▼ :8000
┌───────────────────────────────┐
│ api — FastAPI + uvicorn       │  OpenAPI/Swagger на /docs
│ EmbeddingModel (интерфейс)    │  load() / embed_batch()
│   └─ обученный чекпоинт       │  модель меняется переменной
│                               │  окружения, без правки кода
└───────────────┬───────────────┘
                │ :5432 (наружу не публикуется)
                ▼
┌───────────────────────────────┐
│ db — PostgreSQL 16 + pgvector │  gallery(id, vehicle_id, image_path,
│  HNSW по косинусу             │  bbox, embedding vector(512), created_at)
└───────────────────────────────┘
```

Разделение ответственности: инференс, хранилище и клиент — три отдельных
процесса. Веса поставляются внутри образа, **инференс не требует интернета**.

## 2. Методы обработки данных и алгоритмы

### 2.1 Подготовка данных

Исходные кадры — 11 416 изображений 1920×1080. На каждом размечено ровно одно
ТС. Автомобиль занимает в среднем 16% площади кадра. Поэтому кадры кропаются
по bbox **с запасом 10%** с каждой стороны (чтобы не срезать зеркала, спойлер,
рейлинги — они и есть отличительные признаки), затем **squash** (вся машина
целиком растягивается в квадрат 256×256 — вход ViT-L/16@256). Squash вместо base-кропа даёт +2.9 mAP,
потому что base-кроп срезает перед и зад машины.

### 2.2 Модель

**SigLIP ViT-L/16@256 + ReID-голова**, обученная **дистилляцией** от ансамбля
из 4 моделей (рецепт — раздел 2.7; запасной кандидат на ViT-B/16@224 — ветка `glebmain`).

```
кроп → SigLIP ViT-L/16@256 → 1024 признаков
                              │
              Linear(1024→1024) → BN → ReLU → Dropout(0.3)
                              │
                     Linear(1024→512)
                       │            │
                feat (до BN)   BNNeck (после BN)
                       │            │
           batch-hard triplet   ArcFace
```

- **BNNeck**: triplet работает с вектором до BN, классификация/инференс — после.
- **ArcFace**: угловой зазор между классами — критично для open-set.
- **PK-сэмплер** (P=8, K=1 — у l150 из-за VRAM; у базового a10 K=4): для batch-hard triplet нужны «свои» в батче.
- **Cross-camera**: позитивы в батче берутся с разных камер — позитив не лёгкий.

### 2.3 Дистилляция (ключевой шаг)

Текущая production-модель этой ветки — **clean student ViT-L/16@256 (l150)**,
обученная после удаления пяти exact train↔holdout duplicate-пар. Она дистиллирована
от ансамбля из 4 моделей (SigLIP 2 + SigLIP 1 squash + SigLIP 1 base + CLIP). Учитель
заморожен, его эмбеддинги посчитаны на train-сплите. Ученик:

```
loss = ArcFace + Triplet + 10 · (1 − cos(student, teacher))
```

Эффект: **одна модель**, **без TTA**, 512D; checkpoint —
`clean_student_large_150_ep150.pt` (SHA-256
`6937d1163e239bcfd8ee76fe00da12a9d60becc89563b8fc5a475dc72df13d52`), 150 эпох, seed 7.
Запасной кандидат на ViT-B/16@224 (a10, 362 МБ, ~2× быстрее) — в ветке `glebmain`.

### 2.4 Аугментации (под условия датасета)

| Аугментация | Зачем |
|---|---|
| Снижение яркости/контраста | ~14% кадров ночные, 40% сумерки |
| Локальное пересветление | блики фар и солнца |
| Гауссово размытие | смаз от движения |
| Перекодирование JPEG q25–70 | компрессия камерных комплексов |
| Random erasing | перекрытия |
| Горизонтальное отражение | зеркальные ракурсы |
| Геометрические (перспектива, part-crop, поворот ±7°) | смена ракурса |

### 2.5 Валидация

Протокол повторяет методику жюри (п.9 ТЗ): совпадения в пределах одной камеры
из расчёта исключаются, засчитываются только кросс-камерные.

- 150 машин отложены в валидацию, обучение на остальных 1 391;
- gallery — по одному кадру с каждой камеры, остальные кадры — в query;
- метрики: mAP (основная), Rank-1, Rank-5.

### 2.6 Режим отказа

Production-профиль: ранжирование DBA k=1 без флагов, отказ — сырой косинус (raw) лучшего кандидата без
почти-дублей (фон ИЛИ правило рамок). Порог `0.8249` (строгий `0.9356`) — максимум оценки организаторов
0.7·F1 + 0.3·TNR (Q15) вне фолда на галереях 361 и 361 + 750 кадров обучающих машин, 20 % машин без пары
(Q17), без кадров теста (`docs/refusal.md`). z100 — пресет по выбору (`REFUSAL_SCORE=z100`, 4.4359 / 7.7432). Штраф по фону в
ранжировании убран: эталон засчитывает верным ответ кадром той же машины с той же камеры.

### 2.7 Обучение: как воспроизвести l150

Код обучения — `research/finals_handoff/training/` (`train_reid.py`, `train_distill.py`,
`extract_emb.py`, `evaluate_pair.py`); манифест весов и метрики на чистом holdout —
`research/clean_student/manifest.json`, `research/clean_student/README.md`. Порядок:

1. **Учителя** на чистых строках обучения (без пяти exact-дублей train↔holdout):
   `research/run_clean_retrain.sh` — SigLIP 1 squash, SigLIP 1 base и CLIP через `train_reid.py`
   (30 эпох, чекпоинт эпохи 28). SigLIP 2-учитель (`siglip2_clean_retrain_ep28.pt`) в скрипте не
   записан — тот же `train_reid.py` с `--backbone siglip2_base`; точная команда (строки, гиперпараметры,
   выходной sha) — `research/finals_handoff/TEACHER_PIPELINE_README.md`, шаг 1.
2. **Эмбеддинги учителя** — взвешенный ансамбль четырёх (веса 0.364 / 0.232 / 0.182 / 0.222,
   `manifest.json`) на тех же строках, что в шаге 1: `research/build_clean_teacher.py`
   (веса/tf_mode/TTA — из содержимого config, пример `research/clean_teacher_config.example.json`),
   выход `clean_teacher_emb.npy` 8639×512 float32, sha256 `4ec0e9dc…b60e86d1`
   (команда — `research/finals_handoff/TEACHER_PIPELINE_README.md`, шаг 2).
3. **Студент**: `research/run_clean_student_large.sh` — `train_distill.py`, SigLIP ViT-L/16@256
   (`--backbone siglip_large --input-size 256`, init из публичных весов timm через
   `research/prepare_public_init.py`), squash, `loss = ArcFace + Triplet + α·(1 − cos)`,
   `--alpha 10 --seed 7 --epochs 150`, чекпоинт эпохи 150. Базовый рецепт a10
   (ViT-B/16@224, 28 эпох, кандидат ветки `glebmain`) — `research/run_clean_student_sweep.sh`.
4. Сверить sha256 (l150: `6937d116…`; a10 в `manifest.json`: `93114c59…`).

Пути в скриптах — с машины, где обучали (переменные в начале скриптов): заменить на свои.
Тестовая выборка в обучении не участвует. `kaggle/train_reid.ipynb` (и вариант для Colab,
собираются `kaggle/build_notebooks.py`) — прежний путь дообучения на бесплатной T4; a10 им не
обучался, он нужен для головы под so400m (`scripts/select_profile.sh`).

## 4. Метрики на валидации и обоснование порога

### 4.1 Качество ранжирования

Протокол: 150 машин holdout (`research/val_ids.txt`), 361 gallery, 551 query,
кросс-камерный расчёт, официальный `evaluate.py` организаторов
(`research/official_evaluate.py`), сырой косинус без постобработки.

| Конфигурация | mAP@10 | Rank-1 | Rank-5 | Веса |
|---|---:|---:|---:|---:|
| **Clean student ViT-L/16@256 (l150), alpha=10, 150 эпох** | **0.9005** | **0.8821** | **0.9484** | **~1.21 ГБ** |
| Clean student alpha=10 (a10, ветка `glebmain`) | 0.8661 | 0.8287 | 0.9448 | ~362 МБ |

На стресс-сплите expanded (query дополнены синтетическими искажениями): l150 — mAP@10 **0.6467**,
a10 — 0.5569 (официальный `evaluate.py`; протокол и логи — вне репо, `bm_improve/large_scale/notes.md`,
команда обучения — `research/run_clean_student_large.sh`).

Production (l150 + DBA k=1 по галерее) в протоколе закрытого теста — 546 query, галереи 361 и
1111 (361 + 750 кадров обучающих машин, по кадру на пару машина-камера; кадров теста нет): mAP@10
0.9196 / 0.8207, Rank-1 0.907 / 0.778 (`docs/refusal.md`).

Разбор ошибок с примерами — `research/ERROR_ANALYSIS.md` (коллажи в `research/errors/`): это разбор стартовой модели (CLIP ViT-B/16 + голова, 18.09), а не a10.

Прежние модели считались до clean retrain — на сплите с пятью exact-дублями
train↔holdout (тот же размер: 551 query / 361 gallery), поэтому с таблицей выше не
сравниваются. Прежний студент `siglip2_distill_ensemble_ep28.pt` без постобработки:
0.8581 (`research/GENERALIZATION_RESULTS.md`); в `analysis/DISTILLATION_REPORT.md` для

0.8961–0.8965 / 0.8639 / 0.9637 — с транздуктивной постобработкой qq-expand →
k-reciprocal → CSLS: она использует другие query, что запрещено ответом
организаторов Q38, и в решении больше не применяется. Скорость прежнего студента —
170 мс/кадр на CPU (2 потока), head-only заглушки — 668 мс/кадр, mAP@10 0.6454.

### 4.2 Режим отказа и порог

Production-профиль: ранжирование DBA k=1 без флагов, отказ — сырой косинус (raw) лучшего кандидата без
почти-дублей (фон ИЛИ правило рамок); legacy-порог raw 0.8025 — режим без постобработки. Галереи: 361 кадр
holdout, «750» и «1111» — 361 + 389 / 750 кадров обучающих машин; у 20 % машин в галерее нет ни одного
кадра — как в закрытом тесте (Q17).

| Оценка | Порог | Как выбран | F1 / TNR / полнота 361 | F1 / TNR / полнота 1111 | 0.7·F1+0.3·TNR 361 / 1111 |
|---|---:|---|---:|---:|---:|
| **raw** | **0.8249** | **итог: максимум 0.7·F1 + 0.3·TNR** | **0.857 / 0.945 / 0.761** | **0.845 / 0.680 / 0.795** | **0.883 / 0.796** |
| **raw** | **0.9356** | **строгий: наименьший с TNR ≥ 0.98 на обеих** | 0.483 / 0.996 / 0.320 | 0.486 / 0.969 / 0.326 | 0.637 / 0.631 |
| z100 | 4.4359 | по выбору: то же правило | 0.887 / 0.800 / 0.837 | 0.790 / 0.416 / 0.753 | 0.861 / 0.678 |
| z100 | 4.6506 | прежний (F1 при TNR ≥ 0.70, большая галерея с test gallery, a10) | 0.868 / 0.831 / 0.800 | 0.756 / 0.472 / 0.692 | 0.857 / 0.671 |

Почему raw: по оценке организаторов он лучше z100 и с порогом по своей галерее, и при переносе порога с
одной галереи на другую (строка — где выбран порог, столбцы — где проверен 0.7·F1 + 0.3·TNR):

| Оценка | Порог выбран по | Порог | 361 | 750 | 1111 |
|---|---|---:|---:|---:|---:|
| raw | 361 и 1111 (пресет) | 0.8249 | 0.883 | 0.825 | 0.796 |
| raw | 361 → 1111 | 0.6881 | 0.905 | 0.761 | 0.715 |
| raw | 1111 → 361 | 0.8467 | 0.866 | 0.832 | 0.803 |
| z100 | 361 и 1111 (пресет) | 4.4359 | 0.861 | 0.716 | 0.678 |
| z100 | 361 → 1111 | 4.5670 | 0.858 | 0.721 | 0.674 |
| z100 | 1111 → 361 | 4.1399 | 0.850 | 0.714 | 0.687 |

z100 выбирали раньше — на прежнем протоколе, где большой галереей были кадры test gallery и порог raw при
переносе с 361 терял TNR сильнее. Порог raw растёт с размером галереи: 0.688 по 361,
0.841 по 750 (размер открытого test_gallery, Q27), 0.847 по 1111.
Отвлекатели в 750 и 1111 — обучающие машины (модель их видела), поэтому TNR на них скорее занижен.

Обоснование порога: балл за режим кандидатов — 10 % × (0.7·F1 + 0.3·TNR), F1 и TNR — micro по
запросам, решение — верхний кандидат по confidence (ответы организаторов Q14, Q15, Q19, Q25); в
закрытом тесте у 20 % query пары нет, калибровать — на своём сплите из `train.csv` (Q17). Порог —
максимум среднего 0.7·F1 + 0.3·TNR по 361 и 1111, выбранный вне фолда: 2 фолда по машинам × 5 ротаций,
в конфиг — медиана 10 порогов (`docs/refusal.md`, `research/closed_gallery.py`). **При подборе порога
данные теста не использовались** — ни кадры, ни метки, ни госномер. Строгий порог — для случаев, когда
ложное совпадение дороже пропуска. Запасной без фона — raw 0.8248 / 0.9356.

### 4.3 Смена модели: пороги и веса

Порог отказа (raw 0.8249, строгий 0.9356), порог фона τ 0.68062 и правило почти-дублей (косинус ≥ 0.83,
IoU рамок ≥ 0.6, сдвиг центра ≤ 0.3, |log| отношения сторон ≤ 0.3) подобраны под l150: это косинусы её
векторов. Для другой модели их
нужно пересчитать — одной командой, тем же кодом и по тому же протоколу (Q17, без данных теста):

```bash
EMBED_MODEL=reid:vit_large_patch16_siglip_256 REID_WEIGHTS=/путь/l75.pt INPUT_SIZE=256 \
DATA_DIR=/путь/к/данным DATASET_ZIP=/путь/dataset.zip ./research/recalibrate_for_model.sh l75
```

- `DATA_DIR` — `train.csv`, `test_query.csv` и `test_gallery.csv` (из них читается только таблица рамок) и
  `crops/train/`, если есть; без `crops/` кадры берутся из `DATASET_ZIP` и режутся
  кодом сервиса (так считались пороги l150). Эмбеддинги 9556 кадров `train.csv` считает код сервиса — на GPU в FP16, если есть CUDA, с
  кэшем в `~/lct-case17/cache/honest_eval`; повторный запуск идёт из кэша. Кадры теста не читаются.
- Скрипт (`research/recalibrate_for_model.py`) печатает пресет для `REFUSAL_PRESETS` в `api/app/config.py`,
  строки `.env` и таблицу mAP@10, F1, TNR и 0.7·F1 + 0.3·TNR на 361 и 1111, сверяет их с текущим конфигом и
  пишет всё в `research/honest_eval_results/recalibrate_<имя>.json`. На l150 он даёт числа этой ветки: 0.8249 /
  0.9356, τ 0.68062, рамки 0.83 / 0.6 / 0.3 / 0.3, формула 0.883 / 0.796 (`recalibrate_l150.json`).
- На арендованной A5000 `research/a5000_session.sh` делает это для новой модели и ещё собирает артефакты на GPU, как жюри (`make_submission` в контейнере), и сравнивает с `artifacts/` — sha256, тот же top-1, принятые запросы, confidence, векторы — строкой в `session.md`.

Что поменять в сервисе:

| Где | Что |
|---|---|
| Модель | `EMBED_MODEL`, `REID_WEIGHTS`, `INPUT_SIZE`; `EMBED_DIM` — если размерность выхода другая; `REID_TF_MODE` — режим кропа, на котором модель обучена (у l150 `squash`) |
| Пороги | `SEARCH_THRESHOLD`, `SEARCH_THRESHOLD_STRICT`, `PP_CAMERA_TAU`, `PP_DEDUP_SIM`, `PP_DEDUP_IOU`, `PP_DEDUP_CENTER`, `PP_DEDUP_SIZE` — в `.env` или умолчаниями в `api/app/config.py`; туда же строки `REFUSAL_PRESETS` из вывода скрипта (по ним сервис пишет в лог, что порог не посчитан для текущей постобработки) |
| Артефакты сдачи | пересобрать `api/scripts/make_submission.py` и проверить `scripts/validate_submission.py` |
| Скорость | `api/scripts/bench_extract.py` на новой модели (Q31, Q34): ViT-L в несколько раз тяжелее ViT-B |

Что меняется в весах:

- **Попробовать без пересборки образа:** положить файл в `./weights/` и задать `REID_WEIGHTS=/models/<файл>` —
  том `./weights:/models` из `docker-compose.yml`.
- **В образ (сдача, работа без сети):** имя `clean_student_large_150_ep150.pt` зашито в `api/Dockerfile` (`COPY`,
  `fetch_weights.sh`, `ENV REID_WEIGHTS`), `.dockerignore` (белый список), `docker-compose.yml` (`REID_WEIGHTS`),
  `.env.example`, `.gitattributes` (LFS) и `scripts/check_reproducibility.sh` — заменить на новое.
- **sha256:** новый — в `WEIGHTS_SHA256` (аргумент сборки в `api/Dockerfile`; не совпал — сборка падает) и в
  `REID_WEIGHTS_SHA256` (сверка при старте сервиса); sha256 и размер файла скрипт печатает первой строкой.
- **Размер:** лимит весов — 2 ГБ (Q34, Q37). ViT-L/16 — около 300 млн параметров, в FP32 это ~1.2 ГБ (эта ветка;
  a10 — 94 млн, 362 МБ). В бесплатный Git LFS (1 ГБ на весь репозиторий, a10 уже занимает 362 МБ) такой файл не
  войдёт — только ассет GitHub Release, поэтому в `weights/` этой ветки l150 нет даже указателем LFS.
- **`WEIGHTS_URL`:** ссылка на новый файл с фиксированным тегом релиза (Q39); в README (раздел 5) — URL, автор,
  размер и sha256 модели.

## 6. Производительность (п.7 ТЗ, ответы Q30–Q36)

Организатор меряет на NVIDIA RTX A5000, 24 ГБ, CUDA 12.2, в Docker через `--gpus all` (Q30) полный цикл
`extract()` на одно ТС: чтение файла с диска, декодирование, кроп по bbox, препроцессинг, forward, L2;
поиск по галерее не входит (Q31). latency_b1 — медиана 300 прогонов после 50 прогревочных с
синхронизацией CUDA; throughput — лучший FPS из батчей 1 / 8 / 16 / 32 по ≥ 10 с. Баллы: latency
≤ 40 мс и FPS ≥ 100 — полные, 40–80 мс и 50–100 FPS — линейно (Q34).

Наш `extract()` — `api/app/extractor.py`, замер по этому протоколу — `api/scripts/bench_extract.py`
(latency_b1 медиана и p95, FPS по батчам, пиковый VRAM, время загрузки весов, размер весов по
расширениям из Q37, детерминизм, баллы по Q34). **Команда для замера на A5000:**

```bash
docker compose exec api python scripts/bench_extract.py --out /artifacts/bench_extract.json
# или без compose:
docker run --rm --gpus all --network none -v /путь/к/датасету:/data:ro -v "$PWD/artifacts":/artifacts \
  case17-api:local python scripts/bench_extract.py --out /artifacts/bench_extract.json
```

Ход замера (загрузка модели, sha256 весов, этапы и их итоги) идёт в stderr, в stdout — только итоговый JSON.

## 7. Артефакты сдачи (п.8 ТЗ)

В репозитории (`artifacts/`):

| Файл | Что внутри |
|---|---|
| `submission.csv` | `query_id,gallery_id_1..gallery_id_10` — топ-10 по убыванию близости к галерее после DBA k=1 |
| `embeddings.npy` | float32 `(1110 + 750, 512)`, векторы модели без постобработки, порядок строго как в `test_query.csv` → `test_gallery.csv` |
| `candidates.csv` | `query_id,gallery_id,confidence` — для принятых query top-10 с косинусом, как в ответе `/v1/search`; отказ — строк для query нет |

Собраны моделью l150 тем же кодом, что сервис (`api/scripts/make_submission.py`):
полный кадр + bbox → кроп → l150 → DBA k=1 по галерее → отказ raw без почти-дублей
(фон ИЛИ рамка), порог 0.8249. Каждый query обрабатывается отдельно, другие query
не используются. Принято 814 query, отказов 296 (26.7%). Параметры, sha256 весов и
счёт — в `artifacts/postprocess.json`. Лог прогона — `make_submission.log` в том же каталоге и в stderr,
формат как у сервиса: путь и sha256 весов, устройство, FP16, порог и пресет, время по этапам, принято и
отказов; в git не входит. Одна строка CSV прогон не останавливает: рамка за кадром обрезается
по границам, пустая или уже 2 px — берётся весь кадр, нечитаемый кадр — серый квадрат размера входа; каждый случай —
WARNING / ERROR с image_id, итог — последней строкой лога и в `postprocess.json` (`frame_fixes`);
строк в `embeddings.npy` ровно столько, сколько в CSV (Q27). Так же ведёт себя `extract()`. Проверка происхождения
(`scripts/validate_submission.py`, 27 проверок): `submission.csv` воспроизводится
из `embeddings.npy` (DBA k=1 по галерее) точь-в-точь на всех 1110 запросах; top-1
по векторам без DBA расходится с ним у 2.6% query.

```bash
docker compose exec api python scripts/make_submission.py              # DATA_DIR: test_*.csv + images/
python api/scripts/make_submission.py --zip dataset.zip --out artifacts   # или прямо из архива датасета
```
