# Цифровой признак транспортного средства — решение команды 17

Кейс 17 · ЛЦТ 2026 · заказчик «Фалькон Тех»

Сервис сопоставляет снимки одного автомобиля с разных камер **без использования
государственного номера**, опираясь только на визуальные признаки: тип кузова,
марку и модель, цвет, геометрию, повреждения, наклейки, диски, тонировку.

Этот README соответствует пункту 12 ТЗ (требования к сопроводительной
документации) и пункту 8 (формат сдачи). Все цифры воспроизводимы одной командой.

---

## 1. Функциональная и компонентная архитектура

### 1.1 Функциональный путь запроса (по п.4 ТЗ)

```
[ Этап получения ]   кадр + BBox через REST API или веб-интерфейс,
                     валидация формата, размера и границ рамки
        │
        ▼
[ Этап обработки ]   кроп по BBox с запасом 10% -> squash -> бэкбон -> голова
                     -> эмбеддинг float32, L2-нормированный, 512D
        │
        ▼
[ Этап анализа ]     косинусная близость к галерее после DBA k=1 (pgvector + HNSW)
        │
        ▼
[ Этап результата ]  топ-N кандидатов с оценкой уверенности
                     ЛИБО пустой ответ (отказ), если оценка z100 лучшего
                     кандидата ниже порога (раздел 2.6)
```

### 1.2 Компонентная архитектура (по п.6 ТЗ)

Микросервисная: три независимых контейнера, связь только по сети.

```
браузер (тонкий клиент)
      │ :8080
      ▼
┌───────────────────────────────┐
│ web — nginx + одностраничный  │  выделение BBox мышью, карточки
│ интерфейс, /api/* → api       │  кандидатов, экспорт CSV/JSON
└───────────────┬───────────────┘
                │ внутренняя сеть case17net
                ▼ :8000
┌───────────────────────────────┐
│ api — FastAPI + uvicorn       │  OpenAPI/Swagger на /docs
│ EmbeddingModel (интерфейс)    │  load() / embed_batch()
│   └─ обученный чекпоинт       │  модель меняется переменной
│                               │  окружения, без правки кода
└───────────────┬───────────────┘
                │ :5432 (наружу не публикуется)
                ▼
┌───────────────────────────────┐
│ db — PostgreSQL 16 + pgvector │  gallery(id, vehicle_id, image_path,
│  HNSW по косинусу             │  bbox, embedding vector(512), created_at)
└───────────────────────────────┘
```

Разделение ответственности: инференс, хранилище и клиент — три отдельных
процесса. Веса поставляются внутри образа, **инференс не требует интернета**.

## 2. Методы обработки данных и алгоритмы

### 2.1 Подготовка данных

Исходные кадры — 11 416 изображений 1920×1080. На каждом размечено ровно одно
ТС. Автомобиль занимает в среднем 16% площади кадра. Поэтому кадры кропаются
по bbox **с запасом 10%** с каждой стороны (чтобы не срезать зеркала, спойлер,
рейлинги — они и есть отличительные признаки), затем **squash** (вся машина
целиком растягивается в квадрат 224×224). Squash вместо base-кропа даёт +2.9 mAP,
потому что base-кроп срезает перед и зад машины.

### 2.2 Модель

**SigLIP 2 ViT-B/16 + ReID-голова**, обученная **дистилляцией** от ансамбля
из 4 моделей.

```
кроп → SigLIP 2 ViT-B/16 → 768 признаков
                              │
              Linear(768→1024) → BN → ReLU → Dropout(0.3)
                              │
                     Linear(1024→512)
                       │            │
                feat (до BN)   BNNeck (после BN)
                       │            │
           batch-hard triplet   ArcFace
```

- **BNNeck**: triplet работает с вектором до BN, классификация/инференс — после.
- **ArcFace**: угловой зазор между классами — критично для open-set.
- **PK-сэмплер** (P=8, K=4): для batch-hard triplet нужны «свои» в батче.
- **Cross-camera**: позитивы в батче берутся с разных камер — позитив не лёгкий.

### 2.3 Дистилляция (ключевой шаг)

Текущая production-модель — **clean student alpha=10**, обученная после удаления
пяти exact train↔holdout duplicate-пар. Она дистиллирована от ансамбля из 4
моделей (SigLIP 2 + SigLIP 1 squash + SigLIP 1 base + CLIP). Учитель
заморожен, его эмбеддинги посчитаны на train-сплите. Ученик:

```
loss = ArcFace + Triplet + 10 · (1 − cos(student, teacher))
```

Эффект: **одна модель**, **без TTA**, 512D; checkpoint alpha=10 —
`weights/clean_student_a10_ep28.pt` (SHA-256
`93114c5923869d01e92cd70c2c421f783d05ebdac5652a1f2dc919aa040bf6ce`).

### 2.4 Аугментации (под условия датасета)

| Аугментация | Зачем |
|---|---|
| Снижение яркости/контраста | ~14% кадров ночные, 40% сумерки |
| Локальное пересветление | блики фар и солнца |
| Гауссово размытие | смаз от движения |
| Перекодирование JPEG q25–70 | компрессия камерных комплексов |
| Random erasing | перекрытия |
| Горизонтальное отражение | зеркальные ракурсы |
| Геометрические (перспектива, part-crop, поворот ±7°) | смена ракурса |

### 2.5 Валидация

Протокол повторяет методику жюри (п.9 ТЗ): совпадения в пределах одной камеры
из расчёта исключаются, засчитываются только кросс-камерные.

- 150 машин отложены в валидацию, обучение на остальных 1 391;
- gallery — по одному кадру с каждой камеры, остальные кадры — в query;
- метрики: mAP (основная), Rank-1, Rank-5.

### 2.6 Режим отказа

Production-профиль: ранжирование DBA k=1 без флагов, отказ z100 без почти-дублей (фон ИЛИ правило рамок). Порог `4.6506` (строгий `9.6847`)
выбран вне фолда на галереях 361 / 1111 как в закрытом тесте (`docs/refusal.md`). Штраф по фону в ранжировании
убран: эталон засчитывает верным ответ кадром той же машины с той же камеры (`docs/refusal.md`).

## 3. Запуск одной командой

```bash
git clone <ссылка на репозиторий>
cd case-17-vehicle-digital-signature-team-17
cp .env.example .env          # необязательно: без .env берутся значения по умолчанию
```

Веса модели (`weights/clean_student_a10_ep28.pt`, 362 МБ) лежат в Git LFS и при сборке
запекаются в образ. Два способа их получить — любой из них:

```bash
# 1) через Git LFS
git lfs install && git lfs pull
docker compose up -d

# 2) без git-lfs: скачать при сборке по ссылке (sha256 сверяется, при несовпадении сборка падает)
WEIGHTS_URL=<ссылка на clean_student_a10_ep28.pt> docker compose up -d --build
```

Без обоих сборка остановится с сообщением «укажите WEIGHTS_URL или выполните git lfs pull».
При запуске сеть не нужна: веса и бэкбон уже в образе.

Всё. Интерфейс — http://localhost:8080, Swagger — http://localhost:8000/docs.

Проверка:

```bash
docker compose ps             # все три сервиса healthy
curl -s localhost:8000/ready
```

Артефакты сдачи пересчитываются одной командой:

```bash
docker compose exec api python scripts/make_submission.py
```

Интернет при инференсе не нужен: веса запекаются в образ на этапе сборки (из Git LFS
в `weights/` или по `WEIGHTS_URL`, со сверкой sha256).

## 4. Метрики на валидации и обоснование порога

### 4.1 Качество ранжирования

Протокол: 150 машин holdout (`research/val_ids.txt`), 361 gallery, 551 query,
кросс-камерный расчёт, официальный `evaluate.py` организаторов
(`research/official_evaluate.py`), сырой косинус без постобработки.

| Конфигурация | mAP@10 | Rank-1 | Rank-5 | Веса |
|---|---:|---:|---:|---:|
| **Clean student alpha=10** | **0.8661** | **0.8287** | **0.9448** | **~362 МБ** |

Production (a10 + DBA k=1 по галерее) в протоколе закрытого теста — 546 query,
галереи 361 и 1111 (361 + 750 кадров test gallery как чужие машины): mAP@10
0.8854 / 0.7489, Rank-1 0.857 / 0.689 (`docs/refusal.md`).

Прежние модели считались до clean retrain — на сплите с пятью exact-дублями
train↔holdout (тот же размер: 551 query / 361 gallery), поэтому с таблицей выше не
сравниваются. Прежний студент `siglip2_distill_ensemble_ep28.pt` без постобработки:
0.8581 (`research/GENERALIZATION_RESULTS.md`); в `analysis/DISTILLATION_REPORT.md` для
него же 0.8859 — расхождение источников не разобрано. Встречающиеся в истории
0.8961–0.8965 / 0.8639 / 0.9637 — с транздуктивной постобработкой qq-expand →
k-reciprocal → CSLS: она использует другие query, что запрещено ответом
организаторов Q38, и в решении больше не применяется. Скорость прежнего студента —
170 мс/кадр на CPU (2 потока), head-only заглушки — 668 мс/кадр, mAP@10 0.6454.

### 4.2 Режим отказа и порог

Production-профиль: ранжирование DBA k=1 без флагов, отказ z100 без почти-дублей (фон ИЛИ правило рамок). Пороги 4.6506/9.6847 соответствуют этому
контракту; raw 0.8025 относится к legacy-режиму без постобработки.

| Режим | Score | Порог | F1 361 / 1111 | TNR 361 / 1111 |
|---|---:|---:|---:|---:|
| Production balanced | z100 | 4.6506 | 0.858 / 0.736 | 0.726 / 0.715 |
| Production strict | z100 | 9.6847 | ниже | 0.986 / 0.997 |

Обоснование порога: без ограничения максимум F1 уезжает в «принимать почти всё»
(порог z100 2.71: F1 0.916 / 0.892, но TNR 0.076 / 0.042 на 361 / 1111). Поэтому
порог — максимум среднего F1 при условии TNR ≥ 0.70 одновременно на галереях 361 и
1111, выбранный вне фолда: 2 фолда по машинам × 4 ротации, в конфиг — медиана восьми
порогов (`docs/refusal.md`, `research/closed_gallery.py`). z100, а не сырой косинус:
порог сырого косинуса уезжает с размером галереи (0.659 на 361, 0.783 на 1111), а
размер закрытой галереи неизвестен. Строгий порог 9.6847 — наименьший с TNR ≥ 0.98
на обеих галереях (полнота при нём 0.092 / 0.064 — режим для случаев, когда ложное
совпадение дороже пропуска). Госномер и метки теста для выбора порога не использовались;
кадры test gallery (без меток) входят в галерею 1111 только как чужие машины-отвлекатели.

## 7. Артефакты сдачи (п.8 ТЗ)

В репозитории (`artifacts/`):

| Файл | Что внутри |
|---|---|
| `submission.csv` | `query_id,gallery_id_1..gallery_id_10` — топ-10 по убыванию близости к галерее после DBA k=1 |
| `embeddings.npy` | float32 `(1110 + 750, 512)`, векторы модели без постобработки, порядок строго как в `test_query.csv` → `test_gallery.csv` |
| `candidates.csv` | `query_id,gallery_id,confidence` — для принятых query top-10 с косинусом, как в ответе `/v1/search`; отказ — строк для query нет |

Собраны моделью a10 тем же кодом, что сервис (`api/scripts/make_submission.py`):
полный кадр + bbox → кроп → a10 → DBA k=1 по галерее → отказ z100 без почти-дублей
(фон ИЛИ рамка), порог 4.6506. Каждый query обрабатывается отдельно, другие query
не используются. Принято 784 query, отказов 326 (29.4%). Параметры, sha256 весов и
счёт — в `artifacts/postprocess.json`. Проверка происхождения
(`scripts/validate_submission.py`, 26 проверок): `submission.csv` воспроизводится
из `embeddings.npy` (DBA k=1 по галерее) точь-в-точь на всех 1110 запросах; top-1
по векторам без DBA расходится с ним у 3.8% query.

```bash
docker compose exec api python scripts/make_submission.py              # DATA_DIR: test_*.csv + images/
python api/scripts/make_submission.py --zip dataset.zip --out artifacts   # или прямо из архива датасета
```
