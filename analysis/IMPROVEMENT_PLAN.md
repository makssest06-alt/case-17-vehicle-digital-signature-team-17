### Отдельно: 10% за open-set отказ (candidates.csv)

`mAP` считается только по запросам с позитивом, поэтому:

* `submission.csv` — отдавать топ-10 **для всех** запросов; open-set из mAP
  исключаются, вреда нет, а пропуск запроса с позитивом даёт AP=0;
* `candidates.csv` — только здесь решать отказ.

**Механика оценки важнее, чем кажется.** В `evaluate.py` решение принимается
на уровне запроса, и `F1 = 2TP / (2TP + FP + FN)`. Отказ по запросу, у которого
топ-1 неверен, превращает FP в FN и **F1 не меняет**. Отказ по запросу с верным
топ-1 уменьшает TP и увеличивает FN — **F1 падает**. Значит отказ может помочь
F1 только через запросы без пары в галерее (open-set), иначе он бесполезен или
вреден.

В нашем val-сплите open-set нет вовсе (`val_split.csv` построен нами), поэтому
порог калибруется на синтетическом open-set — часть машин убирается из галереи
(`openset_calib.py`). Оптимум по F1 зависит от доли open-set:

| Доля open-set | Оптимальный отсев | F1 при нём | F1 без отсева |
|---:|---:|---:|---:|
| 0% | 0% | 0.9078 | 0.9078 |
| 5% | 8% | 0.8932 | 0.8815 |
| 10% | 20% | 0.8835 | 0.8518 |
| 25% | 30% | 0.8558 | 0.7775 |

Доля open-set в тесте неизвестна: в `test_query.csv`/`test_gallery.csv` нет
`vehicle_id`, а организаторы метрику TNR предусмотрели — значит open-set
вероятен, но не гарантирован.

Выбран порог **10-й процентиль CSLS-нормированного top-1** — компромисс с
несимметричной ценой ошибки: без open-set он стоит ≤0.006 F1, при 25% open-set
даёт до +0.04. Более агрессивный порог (20–30%) выигрывает больше при большом
open-set, но теряет 0.02–0.04, если open-set нет.

Функция уверенности — CSLS-нормированный top-1 (то, что уже отдаёт конвейер).
Прежние замеры на синтетическом open-set подтверждали, что он разделяет лучше
альтернатив: отрыв top1−top2 давал TNR всего 0.023.

Работает трансдуктивно (обрабатывает query и gallery вместе), что разрешено:
артефакты сдаются файлами `submission.csv` + `embeddings.npy` по всему тесту.

### Точные шаги

```python
import numpy as np

def l2(x):
    return x / (np.linalg.norm(x, axis=-1, keepdims=True) + 1e-12)

# 1. эмбеддинги обеих моделей, L2-нормированные
q29, g29 = l2(emb_ep29_query), l2(emb_ep29_gallery)
qg,  gg  = l2(emb_geom_query), l2(emb_geom_gallery)

# 2. ансамбль: вес geom 0.4
W = 0.4
q = l2((1 - W) * q29 + W * qg)
g = l2((1 - W) * g29 + W * gg)

# 3. расширение запроса его ближайшим ЗАПРОСОМ (не галереей)
sim_qq = q @ q.T
np.fill_diagonal(sim_qq, -np.inf)
nn = np.argmax(sim_qq, axis=1)
q = l2(q + q[nn])                       # k=1, вес 1.0

# 4. CSLS(k=10): вычитаем «типичность» запроса и галереи
S = q @ g.T
k = 10
rq = np.sort(S, axis=1)[:, -k:].mean(axis=1, keepdims=True)
rg = np.sort(S, axis=0)[-k:, :].mean(axis=0, keepdims=True)
S = 2 * S - rq - rg

# 5. k-reciprocal re-ranking (k1=20, k2=6, lambda=0.7) — последним
#    (реализация в case17_data/rerank_test.py: k_reciprocal_rerank)
S = csls(-k_reciprocal_rerank(q, g, k1=20, k2=6, lambda_value=0.7), 10)

# 6. топ-10 по S — в submission.csv
```

Параметры выбирались на одной половине машин и проверялись на другой; при
настройке на A прирост на B составил +4.46, при обратном порядке +4.36.

## 3а. Кадрирование: +2.8 mAP бесплатно, прямо сейчас

**Вывод:** обрезка 33% длины машины стоит дороже, чем искажение пропорций.
Это надо менять в двух местах:

1. **инференс** — подавать squash (и усреднять с base); правка в
   `api/app/models/reid_checkpoint.py` (сейчас там `create_transform`, который
   режет) и в `make_submission.py`;
2. **обучение** — обучать на squash (или хотя бы с `RandomResizedCrop` с полным
   охватом), иначе модель продолжит видеть только центр машины.

Letterbox хуже squash: серые поля дают сдвиг распределения, а искажение
модель переносит лучше.

### Правка инференса (готовый фрагмент)

В `reid_checkpoint.py` сейчас:

```python
cfgd = timm.data.resolve_data_config({}, model=backbone)
cfgd["input_size"] = (3, self.input_size, self.input_size)
self._tf = timm.data.create_transform(**cfgd, is_training=False)   # режет 33%
```

Заменить на прямой ресайз в квадрат (без CenterCrop):

```python
from torchvision import transforms

cfgd = timm.data.resolve_data_config({}, model=backbone)
size = self.input_size
mean = cfgd.get("mean", (0.5, 0.5, 0.5))
std = cfgd.get("std", (0.5, 0.5, 0.5))
self._tf = transforms.Compose([
    transforms.Resize((size, size),
                      interpolation=transforms.InterpolationMode.BICUBIC,
                      antialias=True),
    transforms.ToTensor(),
    transforms.Normalize(mean, std),
])
```

Нормировка та же, что при обучении, — меняется только геометрия. Применять
одинаково к query и gallery.

### Разнообразие ансамбля: что проверено

Выигрыш ансамбля идёт из **разнообразия ошибок**, а не из числа моделей.
Проверены три источника разнообразия:

| Источник | Что делали | Результат |
|---|---|---|
| Другой кроп | squash-модель + base-модели | **+1.29 mAP**, принято |
| Другое разрешение | обучение на 384 | 0.01 mAP, отброшено |
| Другая архитектура | DINOv2 ViT-S/14, 30 эпох | 62.86 одна, **вредит** даже при весе 0.05 |

**DINOv2 отвергнут.** Модель обучена самообучением (иная цель, чем у
контрастивного SigLIP), то есть ошибки должны быть слабо коррелированы —
гипотеза разумная. Но ViT-S/14 вдвое меньше по ёмкости (21M против 86M) и на
8644 кадрах даёт всего 62.86 — на 22 пункта ниже. Слабая модель не
компенсируется разнообразием: при добавлении к смеси с любым весом от 0.05
до 0.20 результат падает (86.79 → 85.96 и ниже).

Вывод: **для ансамбля нужны модели сопоставимой силы**. Разнообразие кропа
сработало потому, что обе base-модели сами по себе давали ~78, а не потому,
что они «другие».

Значения `k1=20, alpha=1.0` выбирались под одиночную geom-модель. У смеси
трёх моделей другая структура сходств, поэтому параметры перепроверены
(`postproc_tune.py`). Опасность: подбор и рапорт на одних и тех же
разбиениях завышает результат, поэтому найденное проверено отдельно
(`postproc_validate.py`) — на разбиениях с другими зёрнами и по схеме
tune/test на непересекающихся половинах машин.

| Параметры | ср. по 40 разб. | парная дельта | лучше в |
|---|---:|---:|---:|
| прежние: k1=20, alpha=1.0 | 86.10 | — | — |
| **новые: k1=30, alpha=3.0** | **86.90** | **+0.79 ± 0.07** | **39/40** |

`k2=3` при этом явно вредит (84.66 против 86.63) и отвергнут. Значения
внесены в `postproc_v2.py` и `reid_postprocess.py` как значения по умолчанию.
На прежней двухмодельной конфигурации эти параметры, наоборот, чуть хуже —
они подобраны именно под трёхмодельную смесь.

**Перенастройка под смесь с SigLIP 2.** Параметры выше подбирались под
прежнюю тройку; у новой смеси другая структура сходств, поэтому подбор
повторён. Тюнер предложил `qk=0` (отключить расширение запроса) и `ck=5`.
Независимая проверка разделила эти две правки:

| Правка | ср. по 40 разб. | парная дельта | лучше в |
|---|---:|---:|---:|
| отключить qq-expand (`qk=0`) | 87.98 (было 87.98) | — | — |
| **CSLS k: 10 → 5** | **89.03** (было 88.39) | **+0.64 ± 0.39** | **39/40** |

Отключение расширения запроса **не подтвердилось** — на разбиениях с другими
зёрнами разницы нет (87.98 против 87.98), то есть тюнер поймал шум на
подгоночных зёрнах. Оставлено включённым. `CSLS k=5` подтверждён парно и
внесён в `postproc_v2.py`.

Общий урок: подбор и отчёт на одних разбиениях систематически завышают
результат, и не всякая найденная правка переживает независимую проверку.

## 4. Что делать в обучении (по убыванию отдачи)

### 4.1. Кроп: модель видит 66.6% длины машины

Трансформ — `Resize(248)` + `CenterCrop(224)`. Для машины с соотношением сторон
1.36 это оставляет только 66.6% длины; у 68.6% машин срезается больше четверти.
Фары, бамперы и номерные знаки в модель не попадают.

**Подтверждено и сделано** (§3а и §3в). Порядок оказался такой:

1. squash на инференсе без переобучения — уже +2.95 mAP (78.45 → 81.40);
2. обучение на squash — ещё +3.36 (81.40 → 84.76 у одиночной модели);
3. ансамбль с base-моделями — ещё +1.29 (84.76 → 86.05).

Letterbox проверен и отвергнут (77.91 против 81.27 у squash): серые поля дают
сдвиг распределения, а искажение пропорций модель переносит лучше.
Не-квадратный вход 224×336 не проверялся — это следующий кандидат.

### 4.2. Сэмплер не сбалансирован по камерам

`PKBatchSampler` набирает K изображений машины подряд из всех камер, поэтому
кросс-камерные позитивы в батче не гарантированы. При кросс-камерной валидации
это прямая потеря. Надо требовать в батче кадры одной машины с разных камер.

### 4.3. Разрешение

Вход всё ещё 224×224 при bbox в среднем 690×500. Переход на 384 требует
дообучения (интерполяция `pos_embed` при инференсе — временная мера).

Скрипт обучения получил флаг `--size`; чекпоинт запоминает разрешение, и
`extract_emb.py` подхватывает его автоматически. `pos_embed` интерполируется
через `dynamic_img_size`, ключи и формы остальных тензоров не меняются —
предобученные веса SigLIP переносятся на 320 и 384 без правок.

Замеры на RTX 3060 (workers=4, AMP, P=8 K=4; VRAM всего ~1.5 ГБ):

| Разрешение | с/шаг | 30 эпох |
|---:|---:|---:|
| 224 | 0.43 | 37 мин |
| 320 | 0.64 | 55 мин |
| 384 | 0.86 | 74 мин |

Память позволяет и больше, но узкое место — декодирование JPEG 1920×1080,
поэтому выигрыш от роста батча невелик. Прогон на 384 запущен; он проверяет,
даёт ли сохранение деталей прирост поверх squash-модели на 224.

**Результат: 384 не даёт прироста.** Прогон оборвался на 16-й эпохе (сервер
перезапустился), но этого достаточно — сравнение на одинаковом конвейере:

| Эпоха | 224 (base / post) | 384 (base / post) |
|---:|---:|---:|
| 16 | — | 78.82 / 83.81 |
| 17 | 79.08 / 83.82 | — |

Разница в 0.01 mAP при том, что база у 384 даже чуть ниже. Траектории
совпадают, то есть после squash разрешение уже не является узким местом:
модель получает достаточно деталей, когда в кадре вся машина, а предел
ставит ёмкость и предобучение, не число пикселей. Перезапуск отменён —
70 минут не окупаются. Флаг `--size` в скрипте оставлен: он пригодится,
если появится датасет с более крупными машинами в кадре.

### 4.4. Part-based ветка

Отдельная ветка на области bbox (верх/низ/полосы), обучаемая end-to-end, без
разметки частей. Бьёт в остаточную путаницу «одинаковых по бренду и цвету» машин.
Отдельные детекторы логотипов и фар не нужны: это признак бренда, а не экземпляра.

### 4.5. Бэкбон: SigLIP 2 вместо SigLIP 1

Самая дешёвая из непроверенных гипотез. SigLIP 2 — прямой преемник SigLIP 1:
та же архитектура ViT-B/16, то есть **прямая замена без переделки рецепта**, но
лучшее предобучение. Лицензия Apache 2.0, как у SigLIP 1, — в сдаваемое решение
годится.

Прежняя заметка «нужен timm ≥ 1.0.15» оказалась неверной: ни 1.0.15, ни 1.0.29
не содержат SigLIP 2 в реестре. Модель тянется с HuggingFace по имени
`vit_base_patch16_siglip_224.v2_webli` — timm умеет разрешать такие имена.
Нужен timm ≥ 1.0.15 именно для этого механизма; проверено на 1.0.29.

Апгрейд timm **безопасен**: эмбеддинги существующих SigLIP 1 чекпоинтов на
1.0.29 совпадают с прежними (расхождение ≤ 2e-6, округление float32).
Проверены оба пути трансформа, а не только новый: `squash` (на
`sq_scratch30_ep26`) и production `timm` = Resize(248)+CenterCrop(224)
(на geom-чекпоинте). Второй важен отдельно — из трёх моделей ансамбля две
идут через него.

Реестр бэкбонов — `case17_data/backbones.py`, ключ `siglip2_base`. Добавить
новый бэкбон = добавить строку в реестр, правок в обучении и оценке не нужно.

**Результат: SigLIP 2 заметно сильнее SigLIP 1.** Тот же рецепт, тот же
датасет, та же длительность (30 эпох, 33 минуты), меняется только бэкбон:

| Модель | base mAP | base R1 | post mAP |
|---|---:|---:|---:|
| sq30 ep26 (SigLIP 1, squash) | 79.68 | 73.50 | 84.75 |
| siglip2 ep28 (SigLIP 2, squash) | 82.85 | 78.04 | 85.94 |
| siglip2 ep30 (SigLIP 2, squash) | **83.08** | **78.40** | 85.40 |

Разрыв в base-метрике (+3.4 mAP) больше, чем после постобработки (+1.2):
постобработка слабой модели помогает сильнее, поэтому она часть разрыва
съедает. Важно, что преимущество лежит в самих признаках, а не вытянуто
постобработкой.

Это лучшая одиночная модель проекта: **85.94 mAP** против 84.75 у прежней.

**В смеси SigLIP 2 добавляет +1.5 mAP** к прежней тройке. Проверено
независимо (`mix4_validate.py`):

| Проверка | Прежняя тройка | Новая смесь | Дельта |
|---|---:|---:|---:|
| Зёрна 100–139 (подбор шёл на 0–19) | 86.90 | **88.39** | +1.49 ± 1.18, лучше в 36/40 |
| Tune на половине машин → test на другой (зерно 7) | 87.20 | **90.34** | +3.14 |
| То же, зерно 21 | 88.06 | **90.46** | +2.40 |

Вторая и третья строки — главные: веса подбирались на одной половине машин,
а выигрыш измерялся на другой. Подгонка под шум так себя не ведёт.

Полный перебор по симплексу (`mix4_grid.py`, 1771 комбинация) показал две
вещи, которые важнее самого максимума:

- **geom-base вытесняется в нулевой вес** — с ним результат тот же, что и
  без него, поэтому в сдаче остаются три модели, а не четыре;
- **ep28 и ep30 в смеси равноценны** (88.21 против 88.03 при весе 0.45 и
  наоборот при 0.55), то есть выбор эпохи на результат не влияет.

Итоговая конфигурация: **siglip2 0.45 + sq30 0.25 + ep29-base 0.30**
(две squash-модели и один base-кроп).

## 5. Репозиторий и воспроизводимость

Скрипт geom-обучения в репозиторий не заложен — в коммите `d108d59` только веса
и README. **Рецепт восстановлен** прямо из чекпоинта: внутри `.pt` лежит ключ
`args` с полным набором параметров прогона.

```
backbone=siglip_base  out_dim=512  hidden=1024  dropout=0.3  loss=arcface
epochs=30  lr_head=3e-4  lr_backbone=1e-5  wd=5e-4  P=8  K=4  warmup=3
amp=true  seed=42  context=0.10  geom_aug=true  tag=siglip_geom_pad10
```

Обучение шло на 8644 кадрах / 1391 машине (тот же `val_ids.txt`, что и валидация).

Скрипт восстановлен в `case17_data/train_reid.py`: geom-аугментации
(перспектива, part-crop, поворот ±7°), опция squash-трансформа,
кросс-камерный сэмплер, тёплый старт из локального чекпоинта.

**Важно:** в чекпоинте лежит полный `state_dict` энкодера timm (162 из 162
тензоров, загружается `strict=True`). Поэтому веса SigLIP не нужно качать из
HuggingFace — обучение полностью офлайновое.

### Проверка воспроизведения (свой код, без готовых `.npy`)

Инференс-путь перепроверен независимо: чекпоинт загружен заново, bbox нарезаны
из исходных кадров, эмбеддинги посчитаны с нуля.

| Конфигурация | base mAP/R1 | +постобработка |
|---|---:|---:|
| geom ep30, timm-трансформ + TTA | 75.54 / 71.51 | 78.37 / 72.78 |
| geom ep30, squash + TTA | 77.34 / 70.96 | **81.40 / 76.23** |
| смесь 0.8·squash + 0.2·base | 78.11 / 71.87 | **82.23 / 76.59** |

Совпадает с числами выше в пределах шума. Вес ансамбля перепроверен по 5
разбиениям: оптимум **w=0.8** (средний mAP 82.36), и это широкое плато 0.7–0.9,
а не подгонка под один сплит.
