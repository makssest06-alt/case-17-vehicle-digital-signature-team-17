# Режим отказа

Схема по умолчанию (команда, 20.10): **ранжирование — DBA k=1 без флагов; отказ — сырой косинус (raw) лучшего кандидата по DBA-галерее, без исключения почти-дублей** (`REFUSAL_SCORE=raw`, `PP_DEDUP_RANK=off`, `PP_DEDUP_REFUSAL=off`), **порог 0.8562** (строгий 0.9294). Запасной пресет — итог 18.10: отказ без почти-дублей «фон ИЛИ правило рамок» (`PP_DEDUP_REFUSAL=both`), порог 0.7586 (строгий 0.9302); почему его сменили — раздел «Почему отказ без исключения почти-дублей». z100 — пресет по выбору (`REFUSAL_SCORE=z100`, порог 4.4294, строгий 9.0723).

## Правило выбора порога — оценка организаторов

Источник — таблица ответов организаторов «Вопросы и ответы Бизнес 7. Фалькон Тех», лист «Объединённые вопросы участников»; номера — оттуда.

- Балл за режим кандидатов — **10 % × (0.7·F1 + 0.3·TNR)** (Q14, Q15). F1 и TNR — micro по запросам, по суммарной матрице ошибок (Q25); решение по запросу — верхний кандидат по confidence (Q19, Q23); TNR = TN / (TN + FP) только по запросам без пары (Q19). Отказ — нет строк query в `candidates.csv` (Q18, Q20); confidence — любая шкала, монотонная по уверенности (Q20, Q26).
- В закрытом тесте у **20 % query соответствующего ТС в gallery нет**, у остальных 80 % гарантирован хотя бы один кросс-камерный позитив; калибровать порог — на своём val-сплите из `train.csv` с ~20 % отложенных ID без пары (Q17, Q6).
- Порог — максимум среднего 0.7·F1 + 0.3·TNR по галереям 361 и 1111, вне фолда; в конфиг — медиана по фолдам × ротациям. Без пары в протоколе 20.0 % запросов.
- **Данные теста при подборе порога не использовались**: ни кадры, ни метки. Галереи — 361 кадр holdout, 750 (+389 кадров обучающих машин) и 1111 (+750 кадров обучающих машин); для запасного пресета порог фона τ = 0.68127 и правило рамок подобраны на парах обучающих машин (`research/honest_eval_results/cheap_bg_a10.md`, `dedup_compare_a10.md`).

## Почему отказ без исключения почти-дублей

В протоколе Q17 у 92 % / 91 % запросов с парой (361 / 1111) первым в ответе стоит кадр той же машины с той же камеры (junk): в галерею идёт первый кадр каждой пары машина–камера, запросы — остальные кадры тех же пар. Ниже — сравнение при трёх трактовках такого ответа; порог в каждой выбран тем же правилом (`research/refusal_topcam.py`, `research/honest_eval_results/refusal_topcam_a10_q17.json`), 0.7·F1 + 0.3·TNR на 361 / 1111:

| Верхний ответ — кадр своей камеры | «DBA» (по умолчанию): порог, 361 / 1111 | итог 18.10 (запасной): порог, 361 / 1111 |
|---|---:|---:|
| засчитывается верным — так считает эталон | 0.8562: **0.933 / 0.891** | 0.7586: 0.881 / 0.756 |
| выкидывается до выбора верхнего | 0.8567: **0.893 / 0.792** | 0.7586: 0.851 / 0.670 |
| считается ошибкой | 0.8862: **0.338 / 0.320** | 0.8868: 0.333 / 0.316 |

«DBA» не хуже прежнего итога ни в одной трактовке. В эталоне (`research/official_evaluate.py`, `candidate_metrics`) верность ответа — только `vehicle_id` верхнего кандидата, то есть трактовка «засчитывается верным» (раздел «Кадр той же камеры в top-1 считается верным»). Если считать такой ответ ошибкой, F1 обеих схем падает почти до нуля; тогда помогло бы только исключение кадров своей камеры из ранжирования, а не из отказа (не считалось).

Прежний итог выигрывает только в сценарии Q22 — у запроса без пары в галерее остался кадр его машины с той же камеры (протокол q15, `closed_gallery_a10_q15.md`): 0.824 / 0.717 против 0.603 / 0.589 у «DBA» на 361 / 1111. По ответу Q22 такой запрос («единственный позитив в gallery оказался junk (та же камера)») исключается из mAP и оценивается только как отказ. В закрытом тесте его нет: по ответу Q17 у 20 % query «соответствующего ТС в gallery» нет совсем, а у остальных 80 % «гарантирован как минимум один кросс-камерный позитив». Поэтому основной протокол — q17, а прежний итог оставлен запасным пресетом (`PP_DEDUP_REFUSAL=both`, `SEARCH_THRESHOLD=0.7586`, `SEARCH_THRESHOLD_STRICT=0.9302`) — на случай, если организаторы уточнят, что такие запросы в закрытой галерее есть.

## Почему raw, а не z100

- **На протоколе по Q17 у «DBA» raw выше z100**: 0.933 / 0.891 против 0.866 / 0.717 на 361 / 1111.
- **Раньше z100 выбрали на прежнем протоколе** (до 18.10): 4 ротации, правило «F1 при TNR ≥ 0.70», большая галерея — 361 + 750 кадров test gallery. Там порог raw, выбранный на 361, на 1111 давал TNR 0.459 против 0.687 у z100 (`closed_gallery_a10.md`).
- **Перенос порога между галереями** (сравнение сделано на итоге 18.10): официальная формула лучше у raw и с порогом, выбранным по своей галерее, и при переносе в обе стороны (таблица: строка — откуда взят порог, столбцы — где проверен).
- **Отвлекатели — обучающие машины**: модель их видела, они сильнее отвлекают, чем невиданные машины закрытого теста, поэтому TNR на 1111 скорее занижен (раздел «Почему на 1111 TNR ниже»).

| Оценка | Порог выбран по | Порог | 0.7·F1+0.3·TNR 361 | 0.7·F1+0.3·TNR 750 | 0.7·F1+0.3·TNR 1111 | TNR 361 / 750 / 1111 |

| raw | 361 и 1111 (**пресет**) | 0.7586 | 0.881 | 0.800 | 0.756 | 0.876 / 0.668 / 0.575 |
| raw | 361 | 0.7142 | 0.882 | 0.772 | 0.724 | 0.830 / 0.538 / 0.441 |
| raw | 750 | 0.7834 | 0.863 | 0.803 | 0.763 | 0.895 / 0.734 / 0.646 |

| z100 | 361 и 1111 (**пресет**) | 4.3475 | 0.842 | 0.704 | 0.671 | 0.747 / 0.470 / 0.476 |

Порог raw растёт с размером галереи — чем больше чужих кадров, тем выше лучший косинус у запроса без пары: 0.714 по 361, 0.783 по 750 (размер открытого test_gallery, Q27), 0.808 по 1111; пресет по 361 и 1111 — 0.759. z100 от размера почти не зависит (4.529 / 4.402 / 4.265), но по формуле проигрывает raw на каждой галерее. При переносе 361 → 1111 у raw TNR падает сильнее (0.441 против 0.517), но полнота растёт больше, и формула всё равно выше: 0.724 против 0.663.

## Что считается отказом

- `/v1/search` отвечает `refusal: true` (`low_similarity`), если оценка уверенности меньше порога, и `gallery_empty`, если галерея пуста. Иначе — кандидаты.
- Метрика эталона (`candidate_metrics`): у запроса без пары отказ — TN, ответ — FP; у запроса с парой ответ с верной машиной на первом месте — TP, с чужой — FP, отказ — FN. Полнота — TP / (TP + FN). PR-AUC — площадь под кривой точность–полнота оценки для «у запроса есть пара», от порога не зависит.

## Оценка уверенности

- `raw` — косинус (по DBA-галерее) лучшего кандидата из top-100; в запасном пресете — лучшего без почти-дублей.
- `z100` = (s1 − mean(s2..s100)) / std(s2..s100) по тем же кандидатам.
- Почти-дубль (запасной пресет): косинус фонов > 0.68127 **или** правило рамок — сырой косинус ≥ 0.84 и IoU рамок ≥ 0.6, сдвиг центра ≤ 0.3 размера рамки. С порогами рамок Андрея (≥ 0.94, или ≥ 0.85 и IoU ≥ 0.7) — 0.882 / 0.876 / 0.816 / 0.880 на 361 и 0.831 / 0.579 / 0.796 / 0.755 на 1111 (F1 / TNR / полнота / оценка).
- Где в конфиге: `api/app/config.py` — `REFUSAL_SCORE`, `SEARCH_THRESHOLD`, `SEARCH_THRESHOLD_STRICT`, `PP_DEDUP_RANK`, `PP_DEDUP_REFUSAL`; посчитанные пороги обеих оценок — `REFUSAL_PRESETS`.

## Кадр той же камеры в top-1 считается верным

В эталоне (`research/official_evaluate.py`) кадр той же машины с той же камеры (junk) вычищается только из ранжирования: п. 1 протокола, `strip_junk` до усечения до 10 — поэтому он не влияет на mAP@10. В `candidate_metrics` его нет: «есть ли пара» считает `valid_positives` (та же машина с другой камеры), а верность ответа — строка 290:

```python
correct = gal_vid.get(top_gid, None) == row.vehicle_id
```

— только `vehicle_id`, камера не сверяется. Штраф по фону в ранжировании (прежний итог) уводил такие кадры из top-1, поэтому фон в ранжирование не идёт:

## Почему на 1111 TNR ниже

Отвлекатели — машины, которые модель видела при обучении. У запроса без пары лучший кандидат оценки отказа — такой кадр в 81 % случаев, его средний скор 0.720 против 0.538 на 361: обученные машины — сильные отвлекатели, отказов меньше (TNR 0.836 против 0.948). В закрытом тесте отвлекатели — невиданные машины, поэтому TNR на 1111 здесь скорее занижен.
