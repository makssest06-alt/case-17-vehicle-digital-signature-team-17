1. Термины и определения 
Для однозначного понимания задачи всеми участниками вводятся следующие ключевые 
понятия: 
• ReID (Re-Identification): Задача повторной идентификации конкретного объекта (в 
данном случае автомобиля) на изображениях, полученных с разных, непересекающихся камер 
наблюдения. 
• Open-set Retrieval (поиск в открытом множестве): Подход, при котором модель должна 
уметь обобщать свои знания и корректно работать с ранее не виденными автомобилями, а не 
просто классифицировать их по заранее известному, фиксированному списку. 
• Эмбеддинг (Embedding): Векторное представление визуальных признаков объекта 
фиксированной размерности, которое позволяет математически сравнивать схожесть разных 
изображений. 
• Bounding Box (BBox): Координаты ограничивающего прямоугольника, который выделяет 
транспортное средство в кадре. Эти координаты предоставляются участникам заранее, чтобы 
сфокусировать задачу именно на идентификации, а не на поиске объекта. 
• Режим отказа (Refusal): Важная продуктовая способность сервиса вернуть пустой ответ 
или сообщение о невозможности идентификации, если в базе данных (галерее) нет уверенного 
совпадения с запросом, вместо того чтобы выдавать ложноположительный результат.

3. Концепция и целевые задачи 
Глобально задача формулируется как поиск по изображению (image retrieval) в открытом 
множестве. Участникам дается галерея (набор изображений транспортных средств с известной 
идентичностью) и запрос (изображение транспортного средства, идентичность которого 
требуется установить). 
Ваше решение должно выполнять следующие целевые задачи: 
1. Формирование признака: Извлечение информативного векторного представления 
(эмбеддинга) из изображения транспортного средства, обрезанного по предоставленным 
координатам BBox. 
2. Ранжирование: Упорядочивание объектов из галереи по убыванию вероятности того, что 
это то же самое транспортное средство, что и на изображении-запросе. 
3. Режим предложения кандидатов: Сервис должен поддерживать реальный продуктовый 
сценарий: возвращать список вероятных совпадений с оценкой уверенности либо давать пустой 
ответ (отказ), если уверенного кандидата в галерее нет. Порог этого отсечения определяется 
участниками самостоятельно и должен быть четко обоснован при защите решения.

4. Функциональные требования 
Работа сервиса должна быть логически разделена на следующие последовательные этапы: 
• Этап получения: Сервис должен принимать на вход изображение и координаты BBox 
через API или пользовательский интерфейс, а также проводить базовую валидацию входных 
данных. 
• Этап обработки: На этом этапе происходит извлечение визуальных признаков. Модель 
генерирует векторный эмбеддинг фиксированной размерности (например, float32) и, 
опционально, классифицирует дополнительные атрибуты автомобиля для повышения точности. 
• Этап анализа: Осуществляется векторный поиск. Эмбеддинг запроса сравнивается с 
базой данных галереи с использованием меры близости, такой как косинусное сходство или 
расстояние L2 по нормированным векторам. Векторы одного и того же ТС, снятого с разных 
камер, должны оказываться математически ближе друг к другу, чем векторы разных ТС. 
• Этап результата: Происходит сортировка кандидатов по убыванию близости. Сервис 
возвращает топ-N наиболее вероятных кандидатов или пустой ответ в случае, если максимальная 
оценка уверенности ниже установленного порога (режим отказа).

8. Формат сдачи результата 
Для корректной проверки и оценки решений участники должны предоставить в свой 
репозиторий следующие артефакты: 
• submission.csv: для каждого запроса упорядоченный список идентификаторов галереи, 
содержащий первые 10 кандидатов по убыванию близости; 
• embeddings.npy: матрица векторов для всех объектов тестовой выборки, сохраненная в 
порядке, строго соответствующем выданному CSV-файлу; 
• candidates.csv: результат работы «режима предложения кандидатов»: для каждого 
запроса список принятых кандидатов с числовыми оценками уверенности либо пустой ответ 
(отказ); 
• код и окружение: исходный код обучения и инференса, dockerfile, docker-compose.yml, 
файл зависимостей. Запуск инференса должен осуществляться одной командой в изолированном 
окружении, при этом решение должно работать без доступа в интернет (все веса поставляются в 
составе решения). 
Механика оценки: Проверка решений проводится организаторами вручную по завершении 
хакатона. Организаторы самостоятельно запускают предоставленные решения на закрытой 
части тестовой выборки с использованием эталонного скрипта расчёта метрики, который будет 
предоставлен участникам заранее. 
 
9. Критерии оценки 
При оценке результатов совпадения в пределах одной точки наблюдения (одной и той же 
камеры) из расчёта исключаются. Засчитываются только кросс-камерные сопоставления, что 
является сутью задачи ReID. Основной метрикой качества является mAP (mean Average 
Precision) по всем запросам. В качестве дополнительных метрик, публикуемых отдельными 
столбцами, используются Rank-1 и Rank-5. 
Для оценки режима предложения кандидатов используются следующие метрики: 
• F1-score при пороге, выбранном командой — основная метрика, балансирующая точность 
и полноту; 
• TNR (True Negative Rate) — доля корректных отказов на запросах, для которых в галерее 
нет совпадения. Это предотвращает ситуацию, когда решение всегда возвращает топ-1 кандидата 
и формально выглядит успешным; 
• mINP или AUC по кривой Precision-Recall — дополнительная метрика, оценивающая 
качество разделения «совпадение/несовпадение» независимо от выбранного порога.

участников части тестовой выборки. Оценивается способность модели обобщать знания и 
корректно идентифицировать ранее не виденные автомобили. 
• Производительность и применимость (20%): соответствие решения требованиям по

допускаются (дисквалификация). 
 
10. Дополнительные возможности 
В случае, если по итогам проверки несколько команд показывают идентичные значения 
основных метрик, жюри использует следующие дополнительные аспекты для определения 
победителя. Эти критерии не добавляют баллов к сумме 100%, а служат исключительно арбитром 
при равенстве результатов. 
• Демонстрационный веб-интерфейс: наличие удобного и наглядного веб-интерфейса, 
позволяющего загрузить изображение-запрос, визуализировать результаты ранжирования, 
увидеть оценку уверенности и экспортировать результаты. Интерфейс должен быть интуитивно 
понятным и демонстрировать продуктовую зрелость решения. 
• Интерпретируемость модели: наличие визуализации (например, с помощью Grad-CAM 
или Attention maps) тех областей изображения, которые наиболее сильно повлияли на решение 
модели о сопоставлении. Это повышает доверие оператора к результатам работы системы. 
• Масштабируемость решения: демонстрация работы приближённого поиска ближайших 
соседей (ANN, например, на базе FAISS или HNSW) для галереи большого порядка (около 10^6 

 
7 
 
объектов), что доказывает готовность решения к реальным городским масштабам без деградации 
скорости. 
• Глубокий анализ ошибок: подробный разбор характерных кейсов неудачного 
сопоставления в документации или во время питча, показывающий глубокое понимание 
ограничений собственной модели и путей её дальнейшего развития. 
 
11. Требования к презентации 
Презентация решения представляется в формате PDF или PPTX и должна быть 
ориентирована как на техническую, так и на бизнес-аудиторию жюри. В ней необходимо отразить: 
• Описание выбранной методологии и архитектуры нейросетей (обоснование выбора

• Наглядную схему пользовательского пути при работе с сервисом. 
• План масштабирования решения для обработки больших объемов данных. 
• Честный и детальный анализ ошибок модели с примерами из тестовой выборки. 
 
12. Требования к сопроводительной документации 
Наличие качественной сопроводительной документации является обязательным условием 
надлежащего решения поставленной задачи. Она должна включать в себя файл Readme.md в 
репозитории и, при необходимости, расширенный PDF-документ, в котором подробно описаны: 
• Детальное описание функциональной и компонентной архитектуры решения. 
• Используемые методы обработки данных и алгоритмы. 
• Пошаговая инструкция по компиляции, сборке и установке, позволяющая запустить 
решение одной командой (например, docker-compose up). 
• Описание метрик, достигнутых на валидационной выборке, и математическое или 
логическое обоснование выбранного порога уверенности для режима отказа. 
• Полный список всех использованных внешних библиотек, фреймворков и датасетов с 
указанием их версий. 
Главная задача этой документации — обеспечить возможность полного воспроизведения 
продемонстрированных результатов сторонним исполнителем или членом жюри.
