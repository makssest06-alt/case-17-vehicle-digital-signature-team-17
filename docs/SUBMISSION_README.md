Кейс 17 · ЛЦТ 2026 · заказчик «Фалькон Тех»

Сервис сопоставляет снимки одного автомобиля с разных камер **без использования
государственного номера**, опираясь только на визуальные признаки: тип кузова,
марку и модель, цвет, геометрию, повреждения, наклейки, диски, тонировку.

## 1. Архитектура решения

### 1.1 Функциональная архитектура

Путь запроса ровно повторяет четыре этапа из пункта 4 ТЗ:

```
   [ Этап получения ]        кадр + BBox через REST API или веб-интерфейс,
                             валидация формата, размера и границ рамки
             │
             ▼
   [ Этап обработки ]        кроп по BBox с запасом 10% -> бэкбон -> голова
                             -> эмбеддинг фиксированной размерности float32,
                             L2-нормированный
             │
             ▼
   [ Этап анализа ]          косинусная близость к галерее;
                             pgvector + HNSW, при малой галерее — точный перебор
             │
             ▼
   [ Этап результата ]       топ-N кандидатов с оценкой уверенности
                             ЛИБО пустой ответ, если максимум ниже порога
```

### 1.2 Компонентная архитектура

Микросервисная, три независимых контейнера — по требованию пункта 6 ТЗ:

```
                       браузер (тонкий клиент)
                              │
                              ▼ :8080
              ┌───────────────────────────────┐
              │  web — nginx + одностраничный │  выделение BBox мышью,
              │  интерфейс без фреймворков    │  карточки кандидатов,
              │  /api/* проксируется на api   │  экспорт CSV/JSON
              └───────────────┬───────────────┘
                              │ внутренняя сеть case17net
                              ▼ :8000
              ┌───────────────────────────────┐
              │  api — FastAPI + uvicorn      │  OpenAPI/Swagger на /docs
              │                               │
              │  EmbeddingModel (интерфейс)   │  load() / embed_batch()
              │    ├─ timm-бэкбон             │  меняется переменной окружения,
              │    └─ обученный чекпоинт      │  без правки кода сервиса
              └───────────────┬───────────────┘
                              │
                              ▼ :5432 (наружу не публикуется)
              ┌───────────────────────────────┐
              │  db — PostgreSQL 16 + pgvector│  gallery(id, vehicle_id,
              │  HNSW по косинусу             │  image_path, bbox,
              │                               │  embedding vector(N), created_at)
              └───────────────────────────────┘
```

Разделение ответственности: инференс, хранилище и клиент — три отдельных
процесса, связанные только по сети. Веса поставляются внутри образа,
**инференс не требует доступа в интернет**.

## 2. Методы обработки данных и алгоритмы

### 2.1 Подготовка данных

Исходные кадры — 11 416 изображений 1920×1080, на каждом размечено ровно одно ТС.
Автомобиль занимает в среднем 16% площади кадра, остальное — фон и чужие машины.

Поэтому первым шагом из кадров один раз вырезаются кропы:

- bbox из CSV **плюс запас 10%** ширины и высоты с каждой стороны, обрезка по
  границам кадра — запас нужен, чтобы не срезать зеркала, спойлер и рейлинги,
  которые как раз являются отличительными признаками;
- ресайз до длинной стороны 512 px, мелкие не увеличиваются;
- JPEG quality 95 без цветовой субдискретизации.

1,1 ГБ вместо 7 ГБ при той же полезной информации.

### 2.2 Модель

```
кроп → <бэкбон> → D признаков
                      │
        Linear(D→1024) → BN → ReLU → Dropout(0.3)
                      │
              Linear(1024→512)
               │            │
        feat (до BN)   BNNeck (после BN)
               │            │
   batch-hard triplet   ArcFace
```

**BNNeck.** Triplet тянет признак в одну сторону, классификационный лосс —
в другую. BatchNorm между ними снимает конфликт: triplet работает с вектором
до нормализации, классификация и инференс — после. Стандартный приём ReID,
дающий заметный прирост почти бесплатно.

**ArcFace** вместо обычного softmax: добавляет угловой зазор между классами,
что для open-set задачи важнее, чем точность классификации на обучающих
идентичностях — на тесте этих машин не будет вовсе.

**Сэмплер P×K** (P машин × K кадров в батче). Без него batch-hard triplet
бессмысленен: ему нужно найти в батче самого далёкого «своего» и самого
близкого «чужого».

**Инференс:** эмбеддинг = среднее векторов оригинала и горизонтального
отражения, затем L2. Даёт устойчивость к зеркальным ракурсам бесплатно.

### 2.3 Аугментации

Подобраны под фактические условия датасета, а не взяты по умолчанию:

| Аугментация | Зачем |
|---|---|
| Снижение яркости и контраста | ~14% кадров ночные, ещё 40% в сумерках |
| Локальное пересветление | блики фар и солнца на кузове |
| Гауссово размытие | смаз от движения |
| Перекодирование JPEG q25–70 | компрессия камерных комплексов |
| Random erasing | перекрытия другими объектами |
| Горизонтальное отражение | зеркальные ракурсы |

### 2.4 Валидация

**Протокол повторяет методику жюри** (пункт 9 ТЗ): совпадения в пределах одной
камеры из расчёта исключаются, засчитываются только кросс-камерные.

- 150 машин (`seed=42`) отложены в валидацию, обучение на остальных 1 391;
- gallery — по одному кадру с каждой камеры, остальные кадры уходят в query;
- кадры с той же камеры, что у запроса, исключаются из выдачи;
- метрики: mAP (основная), Rank-1, Rank-5.

> **Замечание о `camera_id`.** ТЗ (пункт 5) говорит, что идентификатор камеры
> участникам не передаётся. Фактически в выданном `train.csv` семь колонок,
> и `camera_id` среди них есть. Мы используем его **исключительно для построения
> честного валидационного протокола** — чтобы наши цифры совпадали с методикой
> жюри. В инференсе `camera_id` не используется нигде: в тестовой выборке его
> нет, и модель о камере ничего не знает.

### 2.5 Режим отказа

Порог выбирается на контролируемой open-set валидации: половине машин их
собственные кадры убираются из галереи, и получаются запросы, у которых пары
нет в принципе. Дальше измеряется, отделяется ли сходство top-1 у запросов
с парой от запросов без пары.

Метрики — те же, что у жюри (пункт 9 ТЗ): **F1 при выбранном пороге**, **TNR**,
**AUC** как пороговонезависимая оценка разделения.

## 3. Запуск одной командой

```bash
git clone <ссылка на репозиторий>
cd case-17-vehicle-digital-signature-team-17
cp .env.example .env          # при необходимости поменять POSTGRES_PASSWORD
docker compose up -d
```

Всё. Интерфейс — http://localhost:8080, Swagger — http://localhost:8000/docs.

Проверка, что поднялось:

```bash
docker compose ps             # все три сервиса healthy
curl -s localhost:8000/ready
```

Наполнить галерею и получить артефакты сдачи:

```bash
curl -X POST localhost:8000/v1/gallery/bulk-import \
  -H 'Content-Type: application/json' \
  -d '{"images_dir":"/data/crops/gallery","csv_path":"/data/crops/crops_gallery.csv","truncate":true}'

docker compose exec api python scripts/make_submission.py
```

Интернет при инференсе не нужен: веса запечены в образ на этапе сборки.

### 4.2 Обоснование порога отказа

Порог **не подбирался на глаз** и не брался из литературы. Логика такая.

**Шаг 1. Построить честную выборку отказов.** У половины машин из валидации
их собственные кадры убраны из галереи. Получаются два класса запросов:
у одних пара в галерее есть, у других её нет в принципе.

**Шаг 2. Измерить разделимость.** AUC по сходству top-1 показывает, насколько
вообще возможно разделить эти два класса — до всякого выбора порога.

**Шаг 3. Выбрать рабочую точку.** Здесь важная деталь: **при сбалансированных
классах порог, максимизирующий F1, вырождается в «принимать всё»** — полнота
уходит в 1.0, TNR падает почти в ноль, F1 формально высокий. Такой порог
бесполезен и прямо противоречит смыслу пункта 9 ТЗ, где TNR введён именно
чтобы не засчитывать решения, всегда возвращающие топ-1.

Поэтому рабочая точка выбирается по **индексу Юдена** (TPR + TNR − 1),
который штрафует обе ошибки симметрично, а F1 и TNR в этой точке приводятся
как итоговые метрики.

| Модель | AUC | Порог | F1 | Полнота | TNR |
|---|---:|---:|---:|---:|---:|
| **<финальная модель>** | **<...>** | **<...>** | **<...>** | **<...>** | **<...>** |
| CLIP + голова (CosFace 512) | 0.625 | 0.364 | 0.569 | 0.502 | 0.734 |
| CLIP + голова (ArcFace 512) | 0.621 | 0.386 | 0.554 | 0.484 | 0.734 |
| CLIP без головы | 0.534 | 0.836 | 0.547 | 0.556 | 0.518 |

**Шаг 4. Заморозить.** Выбранное значение записано в `SEARCH_THRESHOLD`
в конфигурации и не меняется между запусками.

### 5.4 Внешние датасеты

**Внешние датасеты в обучении не использовались.** Обучение шло только на
выданной организаторами обучающей выборке.

Причина — лицензионная, и она проверена по первоисточникам. Практически все
открытые датасеты ReID автомобилей допускают только некоммерческое
использование:

| Датасет | Лицензия | Решение |
|---|---|---|
| VeRi-776 | доступ по email, non-commercial | не используется |
| VERI-Wild | доступ по email, non-commercial, запрет передачи третьим лицам | не используется |
| VehicleID | non-commercial | не используется |
| BoxCars116k | CC BY-NC-ND 4.0 | не используется |
| CityFlow / AI City | лицензия только в рамках соревнования | не используется |

Веса, обученные на этих датасетах, замерялись **как исследовательский ориентир**
и в поставляемое решение не входят. Подробности — `research/LICENSES.md`.
