## 1. Архитектура решения

### 1.1 Функциональная архитектура

Путь запроса ровно повторяет четыре этапа из пункта 4 ТЗ:

```
   [ Этап получения ]        кадр + BBox через REST API или веб-интерфейс,
                             валидация формата, размера и границ рамки
             │
             ▼
   [ Этап обработки ]        кроп по BBox с запасом 10% -> бэкбон -> голова
                             -> эмбеддинг фиксированной размерности float32,
                             L2-нормированный
             │
             ▼
   [ Этап анализа ]          косинусная близость к галерее;
                             pgvector + HNSW, при малой галерее — точный перебор
             │
             ▼
   [ Этап результата ]       топ-N кандидатов с оценкой уверенности
                             ЛИБО пустой ответ, если максимум ниже порога
```

### 1.2 Компонентная архитектура

Микросервисная, три независимых контейнера — по требованию пункта 6 ТЗ:

```
                       браузер (тонкий клиент)
                              │
                              ▼ :8080
              ┌───────────────────────────────┐
              │  web — nginx + одностраничный │  выделение BBox мышью,
              │  интерфейс без фреймворков    │  карточки кандидатов,
              │  /api/* проксируется на api   │  экспорт CSV/JSON
              └───────────────┬───────────────┘
                              │ внутренняя сеть case17net
                              ▼ :8000
              ┌───────────────────────────────┐
              │  api — FastAPI + uvicorn      │  OpenAPI/Swagger на /docs
              │                               │
              │  EmbeddingModel (интерфейс)   │  load() / embed_batch()
              │    ├─ timm-бэкбон             │  меняется переменной окружения,
              │    └─ обученный чекпоинт      │  без правки кода сервиса
              └───────────────┬───────────────┘
                              │
                              ▼ :5432 (наружу не публикуется)
              ┌───────────────────────────────┐
              │  db — PostgreSQL 16 + pgvector│  gallery(id, vehicle_id,
              │  HNSW по косинусу             │  image_path, bbox,
              │                               │  embedding vector(N), created_at)
              └───────────────────────────────┘
```

Разделение ответственности: инференс, хранилище и клиент — три отдельных
процесса, связанные только по сети. Веса поставляются внутри образа,
**инференс не требует доступа в интернет**.

## 2. Методы обработки данных и алгоритмы

### 2.1 Подготовка данных

Исходные кадры — 11 416 изображений 1920×1080, на каждом размечено ровно одно ТС.
Автомобиль занимает в среднем 16% площади кадра, остальное — фон и чужие машины.

Поэтому первым шагом из кадров один раз вырезаются кропы:

- bbox из CSV **плюс запас 10%** ширины и высоты с каждой стороны, обрезка по
  границам кадра — запас нужен, чтобы не срезать зеркала, спойлер и рейлинги,
  которые как раз являются отличительными признаками;
- ресайз до длинной стороны 512 px, мелкие не увеличиваются;
- JPEG quality 95 без цветовой субдискретизации.

1,1 ГБ вместо 7 ГБ при той же полезной информации.

### 2.2 Модель

```
кроп → <бэкбон> → D признаков
                      │
        Linear(D→1024) → BN → ReLU → Dropout(0.3)
                      │
              Linear(1024→512)
               │            │
        feat (до BN)   BNNeck (после BN)
               │            │
   batch-hard triplet   ArcFace
```

**BNNeck.** Triplet тянет признак в одну сторону, классификационный лосс —
в другую. BatchNorm между ними снимает конфликт: triplet работает с вектором
до нормализации, классификация и инференс — после. Стандартный приём ReID,
дающий заметный прирост почти бесплатно.

**ArcFace** вместо обычного softmax: добавляет угловой зазор между классами,
что для open-set задачи важнее, чем точность классификации на обучающих
идентичностях — на тесте этих машин не будет вовсе.

**Сэмплер P×K** (P машин × K кадров в батче). Без него batch-hard triplet
бессмысленен: ему нужно найти в батче самого далёкого «своего» и самого
близкого «чужого».

**Инференс:** эмбеддинг = среднее векторов оригинала и горизонтального
отражения, затем L2. Даёт устойчивость к зеркальным ракурсам бесплатно.

### 2.3 Аугментации

Подобраны под фактические условия датасета, а не взяты по умолчанию:

| Аугментация | Зачем |
|---|---|
| Снижение яркости и контраста | ~14% кадров ночные, ещё 40% в сумерках |
| Локальное пересветление | блики фар и солнца на кузове |
| Гауссово размытие | смаз от движения |
| Перекодирование JPEG q25–70 | компрессия камерных комплексов |
| Random erasing | перекрытия другими объектами |
| Горизонтальное отражение | зеркальные ракурсы |

### 2.4 Валидация

**Протокол повторяет методику жюри** (пункт 9 ТЗ): совпадения в пределах одной
камеры из расчёта исключаются, засчитываются только кросс-камерные.

- 150 машин (`seed=42`) отложены в валидацию, обучение на остальных 1 391;
- gallery — по одному кадру с каждой камеры, остальные кадры уходят в query;
- кадры с той же камеры, что у запроса, исключаются из выдачи;
- метрики: mAP (основная), Rank-1, Rank-5.

> **Замечание о `camera_id`.** ТЗ (пункт 5) говорит, что идентификатор камеры
> участникам не передаётся. Фактически в выданном `train.csv` семь колонок,
> и `camera_id` среди них есть. Мы используем его **исключительно для построения
> честного валидационного протокола** — чтобы наши цифры совпадали с методикой
> жюри. В инференсе `camera_id` не используется нигде: в тестовой выборке его
> нет, и модель о камере ничего не знает.

### 2.5 Режим отказа

Порог выбирается на контролируемой open-set валидации: половине машин их
собственные кадры убираются из галереи, и получаются запросы, у которых пары
нет в принципе. Дальше измеряется, отделяется ли сходство top-1 у запросов
с парой от запросов без пары.

Метрики — те же, что у жюри (пункт 9 ТЗ): **F1 при выбранном пороге**, **TNR**,
**AUC** как пороговонезависимая оценка разделения.

### 4.1 Качество ранжирования

Протокол из раздела 2.4: 150 машин, 361 gallery, 551 query, кросс-камерный расчёт,
официальный `evaluate.py` организаторов.

Финальная модель — **дистиллированный студент**: SigLIP 2 ViT-B/16, обученный

### 4.1а. Ошибка, которую мы нашли у себя за четыре дня до сдачи

Голова обучалась на выходах бэкбона, которые `research/extract_features.py`
L2-нормирует перед сохранением. Сервис подавал в голову **сырой** выход
бэкбона. Внешне всё работало: сервис отвечал, отказ срабатывал, метрики
выглядели правдоподобно. Но один и тот же кадр давал косинус 0.57 между
выгрузкой признаков и ответом сервиса, и это было видно только если сравнить
два пути напрямую.

Цена ошибки, замер `research/service_path_extras.py`:

| Вход в голову | mAP | Rank-1 | Rank-5 | Катастроф |
|---|---:|---:|---:|---:|
| сырой выход бэкбона (было) | 61.52 | 57.17 | 76.95 | 7.6% |
| **L2-нормированный (как училась голова)** | **64.54** | **59.71** | **80.04** | **3.8%** |

Исправление — одна строка в `api/app/models/reid_checkpoint.py`, метод
`_encode`. Вывод, который мы из этого делаем и который стоит дороже трёх
пунктов mAP: **метрику нельзя мерить по выгрузке признаков, если отвечает
сервис**. Теперь она меряется сервисным путём, и этот скрипт лежит в репозитории.

### 4.2 Обоснование порога отказа

Порог **не подбирался на глаз** и не брался из литературы. Логика такая.

**Шаг 0. Выбрать протокол, в котором порог вообще имеет смысл.** Это не
формальность, мы на этом обожглись. Метрики ранжирования считаются
кросс-камерно: совпадения внутри одной камеры исключаются, иначе задача
вырождается в поиск соседнего кадра. Но **порог отказа так калибровать
нельзя**: по пункту 5 ТЗ `camera_id` на вход не подаётся, значит сервис
физически не может отфильтровать свою камеру и видит галерею целиком.

Порог, снятый с кросс-камерного распределения, оказался 0.595 — а на боевой
выдаче минимальное сходство top-1 равно 0.840. То есть такой порог **не
отказывает никогда**, и TNR на тесте жюри был бы нулевым. Поэтому порог
калибруется на том же распределении, в котором работает сервис: галерея
не фильтруется.

| Протокол | AUC | Порог | F1 | Полнота | TNR |
|---|---:|---:|---:|---:|---:|
| Кросс-камерный (как считается mAP) | 0.8697 | 0.5950 | 0.819 | 0.869 | 0.746 |
| **Как работает сервис (берём его)** | **0.9865** | **0.8025** | **0.946** | **0.931** | **0.964** |

Обе строки честные, просто меряют разное: первая — насколько трудно узнать
машину с другой камеры, вторая — насколько надёжно сервис отличает «нашёл»
от «такой машины тут нет». Для режима отказа по ТЗ нужна вторая.

**Шаг 1. Построить честную выборку отказов.** Для каждого запроса его машина
убирается из галереи (leave-one-vehicle-out). Получаются два класса запросов:
у одних пара в галерее есть, у других её нет в принципе. Выборка 551 на 551,
сбалансированная.

**Шаг 2. Измерить разделимость.** AUC по сходству top-1 показывает, насколько
вообще возможно разделить эти два класса — до всякого выбора порога.
У студента **AUC 0.9865** в рабочем протоколе: распределения почти не
перекрываются (медиана позитивов 0.967, медиана негативов 0.512).

**Шаг 3. Выбрать рабочую точку.** Здесь важная деталь: **при сбалансированных
классах порог, максимизирующий F1, вырождается в «принимать всё»** — полнота
уходит в 1.0, TNR падает почти в ноль, F1 формально высокий. Такой порог
бесполезен и прямо противоречит смыслу пункта 9 ТЗ, где TNR введён именно
чтобы не засчитывать решения, всегда возвращающие топ-1.

Поэтому рабочая точка выбирается по **индексу Юдена** (TPR + TNR − 1),
который штрафует обе ошибки симметрично, а F1 и TNR в этой точке приводятся
как итоговые метрики. У студента оба критерия сошлись в одной точке — 0.8025.

Итоговые цифры в рабочем протоколе:

| Модель | AUC | Порог | F1 | Полнота | TNR |
|---|---:|---:|---:|---:|---:|
| **Дистиллированный студент (финальная)** | **0.9865** | **0.8025** | **0.946** | **0.931** | **0.964** |
| прежняя head-only модель | 0.9720 | 0.5114 | 0.934 | 0.939 | 0.927 |

Картинка с обоими распределениями и обеими рабочими точками —
`research/pitch_assets/05_refusal.png`. Строится `research/make_pitch_assets.py`
из оценок отказов, которые генерирует `research/service_path_extras.py`
(промежуточный файл `refusal_scores_service.npz` в репозиторий не коммитится —
он пересчитывается на финальной модели).

Для сравнения — та же финальная модель в кросс-камерном протоколе, где задача
заметно труднее: AUC 0.8697, оптимум Юдена 0.595 при F1 0.819 и TNR 0.746.

**Шаг 4. Заморозить.** Выбранное значение записано в `SEARCH_THRESHOLD`
в конфигурации и не меняется между запусками.

Распределения сходства — `research/refusal_deployment.png` (рабочий протокол)
и `research/refusal_siglip.png` (кросс-камерный).

Воспроизвести:

```bash
python research/eval_refusal.py --backbone siglip_base --heads p_baseline \
  --protocol deployment --out refusal_deployment.png
```

### 4.3 Две рабочие точки порога, а не одна

Порог — это продуктовое решение, а не техническая константа, поэтому мы
фиксируем две точки и выносим выбор в интерфейс:

| Режим | Порог | F1 | Точность | Полнота | TNR |
|---|---:|---:|---:|---:|---:|
| **сбалансированный** (по умолчанию) | 0.8025 | **0.946** | 0.962 | **0.931** | 0.964 |
| **строгий** | 0.8465 | 0.935 | **0.982** | 0.893 | **0.984** |

Сбалансированный — максимум индекса Юдена, обе ошибки равноценны. Строгий для
случая, когда ложное совпадение дороже пропуска: из шестидесяти чужих запросов
ошибочно принимается примерно один, и ценой всего четырёх пунктов полноты.

Пересчитать под другую модель: `python research/operating_points.py <тег головы>`.
Интерфейс берёт пороги из `GET /v1/config`, зашитых чисел в нём нет.

## 4а. Развилка по железу: какая модель на каком стенде

Решение параметризовано по бэкбону, поэтому под разное железо идёт разная
модель, и переключение — одна переменная `EMBED_MODEL` плюс пересборка образа
(веса бэкбона запекаются внутрь).

| Стенд | Бэкбон | Весов | mAP | Скорость |
|---|---|---:|---:|---:|
| **без GPU** (наш случай) | дистиллированный студент SigLIP 2 ViT-B/16 | 362 МБ | **0.8961** | ~5.9 кадра/с на 2 vCPU |
| **с GPU** | SigLIP so400m + голова | 1638 МБ | ожидаем выше | см. расчёт ниже |

Выбрать автоматически:

```bash
./scripts/select_profile.sh          # определить железо и проставить профиль
./scripts/select_profile.sh --show   # посмотреть текущий
docker compose up -d --build         # применить
```

**Почему so400m не включён по умолчанию, хотя видеокарта его потянет.**
Обученной головы под so400m у нас пока нет: он замерен только zero-shot и даёт
**mAP 60.80 — это почти на 29 пунктов ХУЖЕ**, чем наш финальный студент (0.8961).
Поэтому `select_profile.sh gpu` при отсутствии головы честно остаётся на
CPU-профиле и говорит почему, а не переключается молча в худшую конфигурацию.
Голова под so400m обучается тем же ноутбуком `kaggle/train_reid.ipynb` —
достаточно поменять `backbone` в ячейке `CFG`.

**Проверка лимита весов.** so400m это 1631 МБ, голова поверх 1152-мерных
признаков — 1,71 млн параметров, то есть 6,5 МБ в fp32. **Итого 1638 МБ при
лимите 2048 МБ по ТЗ**, запас 410 МБ (20%). Влезает, но впритык: на fp32-граф
ONNX места ещё хватает, на вторую модель рядом — уже нет.

**Оценка скорости на GPU.** Видеокарты у нас нет, поэтому это расчёт, а не
замер, и мы отмечаем это прямо:

* по вычислениям so400m тяжелее base примерно **в 6 раз** (256 токенов против
  196, ширина 1152 против 768, 27 слоёв против 12);
* наш замер на CPU даёт отношение **8,1x** (2.85 против 0.35 кадра/с) — больше
  шести, потому что на CPU добавляется упор в память;
* на видеокарте задача становится чисто вычислительной, поэтому отношение
  должно приблизиться к **6x**.

Отсюда: если на стенде base выдаёт X кадров в секунду, so400m выдаст примерно
X/6. Для ориентира, ViT-B/16 на T4 через ONNX Runtime обычно даёт сотни кадров
в секунду при батче 32 — значит so400m это десятки, что для потока с камер
с запасом достаточно. **Этот абзац — арифметика по числу операций, а не замер;
как только появится доступ к карте, здесь встанут измеренные цифры.**

Профиль ДО/ПОСЛЕ показывает, почему GPU вообще решает: **97% времени запроса
занимает модель**, и это ровно та часть, которую ускоряет видеокарта. Все
остальные семь этапов вместе — 11 мс из 320.

## 4б. Артефакты сдачи: формат, порядок и проверка

Артефакты пересчитываются одной командой и проверяются другой:

```bash
docker compose exec api python scripts/make_submission.py   # собрать
python scripts/validate_submission.py                       # проверить
```

Валидатор прогоняет 24 проверки: заголовки, число строк, порядок, размерности,
нормы, дубли, диапазон уверенности, монотонность, наличие файлов в репозитории
и сквозную сверку submission против embeddings. Он запускается перед каждым
коммитом артефактов, и без зелёного результата артефакты не коммитятся.

**Порядок строк — часть контракта, и мы на нём обожглись.** README датасета
требует: в `embeddings.npy` сначала все `image_id` из `test_query.csv` в порядке
файла, затем все из `test_gallery.csv`. Наши рабочие `crops_*.csv` отсортированы
по `image_id`, и первая версия артефактов легла в этом порядке — множества
совпадали, последовательность нет. Организаторы сверяют submission с векторами
именно по этому порядку, так что проверка бы не прошла. Теперь порядок берётся
из исходных csv датасета, фиксируется в `artifacts/embeddings_index.csv` и
проверяется автоматически.

**Почему в артефактах нет пересортировки выдачи.** k-reciprocal re-ranking даёт
+3.16 mAP на валидации, и код для него есть (`make_submission.py --rerank`). Но
он меняет топ-1 примерно у 11% запросов, и тогда топ-1 в `submission.csv`
перестаёт совпадать с топ-1, который даёт `embeddings.npy`. README датасета
прямо говорит, что организаторы используют векторы для проверки происхождения
submission. Мы посчитали три пункта mAP меньшей ценностью, чем риск не пройти
эту проверку, и по умолчанию собираем артефакты без пересортировки — топ-1
сходится на 100% проб. Решение обратимое: один флаг.
